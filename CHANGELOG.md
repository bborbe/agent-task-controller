# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

- fix: **record both paths when a create writes a second file carrying an identifier the index already maps elsewhere, so later writes refuse instead of landing on the old file.** `recordCreatedTaskPath` skipped recording on any index hit, and a trigger-only controller (`POLL_INTERVAL=0s`) never rebuilds its index, so the new file stayed invisible for the pod's life and every result and frontmatter write resolved to the old one — measured 2026-10-27 on identifier 9371a3d2, where the executor's spawn write landed on an aborted file while the live one was unrecorded. A hit at a different path now re-reads the indexed file: if it still carries the identifier, the new `TaskPathResolver.RecordDuplicate` adds the second path beside it so `Resolve` reports the duplicate and `FindTaskFilePath` refuses, with a warning naming both paths; if it no longer does, the stale entry is replaced, because a false duplicate in a never-rebuilt index would block every write for that identifier. An occupant that cannot be read or parsed is *not* treated as absent: a transient git-rest error keeps the existing entry, because replacing on a failed read would restore the exact misroute this change closes. `Record` keeps its replace semantics for the walk path.

## v0.22.2

- fix: **a ref-bearing task with no `max_triggers` is now escalated when it reaches the trigger cap instead of parking silently with a live assignee.** The executor refuses such a task once `trigger_count >= MaxTriggers()` (the lib default 3) because `checkTriggerBudget` treats a `ref` as opting in, but both escalation sites gated on `max_triggers` being present and so stayed silent — leaving the record at its lifecycle phase with an assignee and no job (seven `pr-review` records in `seibert-agent`, measured 2026-10-27). Both sites now use the exported `result.TriggerCapEngaged` — `(max_triggers present || ref present) && triggerCount >= MaxTriggers()` — matching the refusal predicate: `applyTriggerCap` in the result writer, and `NewIncrementFrontmatterExecutor`, which is the only site the deadline-failure (`PublishFailure` → `IncrementFrontmatterCommand`) path reaches. **Either alone is insufficient**: the result writer is reachable only from `WriteResult` (the agent-result path), so a zombie deadline failure never touches it. The escalation clears the assignee through the shared `clearAssignee` chokepoint (captured into `previous_assignee`, so the operator-inbox `assignee == ""` filter surfaces it) and appends the `## Trigger Cap Escalation` section; it does not route to `human_review` (no Config admits that phase). The increment executor writes the body section before the frontmatter PATCH — the PATCH carries a delta, so a failed PUT after a landed PATCH would re-increment on redelivery — and re-reads the task immediately before the PUT so a concurrent `## Failure` write is merged onto rather than clobbered.

## v0.22.1

- fix: **a re-emit under a new title no longer creates a second file for the same task_identifier.** Before posting a create, the executor resolves the command's identifier against the identifier→path index and, on a clean hit, posts the create under the title stem of the file that already carries it — so a retitled PR or a diverged title SHA lands on the occupied path and receives the server's existing conflict/reopen answer instead of materializing a second file that shares one identity. A miss, a nil resolver and a resolver error keep the command's own title; the ambiguity is logged and never redirects. Measured 2026-10-27 in the prod task store: 16 identifiers across 35 files, and all five stuck `github-update-go` records were members of such a group.

## v0.22.0

- refactor: **the create executor writes through the typed API, and the git-based create path is deleted.** `createThroughAPI` sends one create and settles the three outcomes from the answer: created, reopened, or a 409 naming the occupant. The title-path pre-check, the create-only/upsert split, the disambiguation re-check and the file-content builder are gone — the server owns the filename, the write and the commit message, so the controller no longer reads the vault to decide what to write. The recurring carve-out survives as one branch: a terminal recurring instance holds its slot, because the title-path file *is* the dedupe state, and that branch now runs before disambiguation — without it the next hourly tick would create a second file next to every completed instance (the v0.6.0 regression). `vaultapi.IsTerminalStatus` exposes the two protocol values that conflict answer needs.
  ℹ️ Three things the first cut got wrong and the review caught. A conflict on the **second** (disambiguated) create was wrapped as a generic error: on replay of a disambiguated task the suffixed path holds this task's own file, and result-topic consumers special-case `task.ErrTaskAlreadyExists` — anything else is a real Failure. It now maps to the same sentinel. The reopen audit line had been demoted to `V(2)`: a reopen replaces a task an operator already closed, so it is back to an unconditional `Infof` (the prior status is no longer available — the server replaces the file and reports only that it did). And the result path is now derived from the title the create actually used rather than the server's echoed `Title`, since a normalised or empty echo would have recorded the wrong path and let the just-created task be retired by its own supersede scan. That path is joined with no further check on purpose: `createTaskTitle` already rejects separators *before* the create, `cmd.Validate` already rejects `..`, and `.md` is appended — so nothing reaching the join can traverse, and any check that could fail after the create would strand a materialized task that the index and the supersede hooks never see. `IsTerminalStatus` reads its two values from `domain`'s typed constants rather than re-spelling them.
  ℹ️ The suite is re-pointed at the disk the fake API writes instead of the git fake's stubs: the occupancy specs seed a real occupant and the write assertions read the file back. Two specs were retired because their subject moved into vault-api (the reopen-vs-create commit message); the reopen *behaviour* they shadowed stays pinned by the terminal-reopen, byte-identical and replay-idempotency specs. Mutation-verified: disabling the recurring carve-out fails exactly the two recurring specs, dropping the disambiguation suffix fails exactly the two collision specs, reverting the fake's fail-closed parse fails exactly the two unparseable-occupant entries, dropping the second-create sentinel fails exactly its new spec, and sourcing the path from the server echo fails exactly the new echo spec.

## v0.21.0

- feat: **the typed client can reopen a terminal task and re-address a task by identifier, and its create conflict now names the occupant.** Three additions the remaining call sites need, mirroring `bborbe/vault-api`'s new surface. `CreateTask` takes a `CreateOptions{ReopenTerminal}` so the reopen mode is opt-in — the zero value is the route's original contract, where any occupant is a conflict, and a spec pins that an ordinary create never sends the field. `ReaddressTask` moves a task to a new identifier without moving its file, which is what the planning-retry's per-attempt identifier needs and what `PATCH` refuses by design. And a create conflict now returns `*AlreadyExistsError` carrying the occupant's `task_identifier` and `status`: the 409's own `id` is the title the caller just sent, so it told the caller nothing, and the create executor cannot otherwise tell "same task, terminal, reopen" from "different task, disambiguate the title". `Unwrap` reports `ErrAlreadyExists`, so `errors.Is` is unchanged for every existing caller.
  ℹ️ `pkg/vaultapi` had **no tests at all** before this change; the new methods are covered by a spec suite that asserts the wire shape (method, path, body, gateway header) against a recording server, plus both conflict shapes. The opt-in claim is mutation-verified: making `reopen` unconditional fails the ordinary-create spec and only that spec.

## v0.20.1

- test: **the body re-read is now pinned by a spec that fails if the section is merged onto the stale read.** The v0.20.0 fix could be undone without any test noticing: the complete-task suite only asserted `ReadTaskCallCount() == 2`, so swapping `resolutionBody(fresh.Body, …)` back to `resolutionBody(found.Body, …)` passed. A stale-first-read stub now returns the older body on the first read and the operator's edited body on the re-read, and the spec asserts the edit survives the PUT. The same gap in the update-frontmatter read-failure spec is closed — it stubbed every read, so the first one failed and the re-read branch it was meant to cover was never reached; it now fails only the second read and asserts the PATCH had already landed. Adds specs for the two branches the fix introduced (a re-read failing after the PATCH, and a concurrent close that must skip the body write rather than append a second `## Resolution`), and addresses the body PUT by the re-read task's id rather than the stale one.

- fix: **the update-frontmatter body PUT is addressed by the re-read task's id, not the one from the initial read.** `applyUpdate` re-reads the task before its PUT so the section merges onto a fresh body, but then wrote that body to `task.ID` — the id carried by the read at the top of the executor. If the task were deleted and recreated under the same identifier between the two reads, the fresh body would land on the stale record. It now writes to `fresh.ID`, which is the same hardening the complete-task executor received in v0.20.0; a spec pins it by stubbing the two reads to return differing ids and asserting the PUT's id argument, and the assertion is mutation-verified (reverting to `task.ID` fails it with `stale-id` where `fresh-id` was expected).

## v0.20.0

- feat: **the update-frontmatter command addresses the task by `task_identifier` and PATCHes only the fields it changes, instead of walking the vault for a path and rewriting the whole file.** `NewUpdateFrontmatterExecutor` takes a `pkg/vaultapi.Client` in place of `GitClient`/`taskDir`/`resolver`: it reads the task by identifier, sends the command's `Updates` plus the two doctrines (spec 042's `phase: human_review` ⇒ `assignee: ""`, and the `target_vault` heal) as one field-level `PATCH /tasks/{id}`, and PUTs the body only when the command carries a body section — so frontmatter the command never names cannot be rewritten at all, which the old whole-file merge could only approximate by merging carefully. Two consequences are named rather than hidden: the write is **two requests, not one atomic commit** (a failure between them leaves frontmatter updated and the body stale; the command is redelivered and both halves are idempotent), and the patch is computed from the read that precedes it, so a concurrent writer's change to a named field inside that one-round-trip window is overwritten. The diff that builds the patch compares values with `result.FrontmatterValueEqual`, never `!=`: frontmatter arrives JSON-decoded, so a task carrying `tags:` holds `[]any` on both sides and `!=` panics with `comparing uncomparable type []interface {}` — for every update command against that task, not only ones naming the list. That is the hazard `pkg/result` already documented for its own merge, so the helper is now exported and shared.

- fix: **the update-frontmatter body PUT re-reads the task before merging its section, so an edit that lands between the read and the write is no longer silently dropped.** `PUT /tasks/{id}/content` replaces the whole body, and the port merged the command's section onto the body captured by the `ReadTask` at the top of the executor — so any body change made in that one-round-trip window was overwritten, which the replaced `AtomicReadModifyWriteAndCommitPush` could not do because its modify closure re-read the file at write time. The body half now re-reads the task immediately before the PUT and merges onto that; a re-read failure is returned rather than falling back to the stale snapshot, so the command retries. This is the body-side counterpart of the frontmatter window the port already documented. Also pins the two error paths the port introduced (`ReadTask` failing with anything but `ErrNotFound`, and a rejected `PATCH` — both must surface and increment the `error` outcome), and corrects the shared test fake's doc comment, which still claimed only `ReadTask` and `PatchTask` were wired.

- fix: **the complete-task body write re-reads the task too, and re-checks its own idempotency guard on the fresh body.** Same window as the update executor: `PUT` replaces the whole body, so appending the `## Resolution` section to the body captured at the top of the command would drop any edit made in between. The re-read also closes a second hole — a concurrent close landing in that window would otherwise gain a second `## Resolution` section, because the guard had already been evaluated against the older body. The recovery this executor documents is now stated with its bound: a failure between `PATCH` and `PUT` leaves the task `completed` with no Resolution, a retry repairs it, but a command that expires first (`commandExpireDuration`, 60 min) leaves that partial state permanently — `PATCH`-before-`PUT` is still the right order, since `PUT`-first would make the body guard skip the `PATCH` forever. Three specs pin the failure modes (`PATCH` rejected leaves the task open; `PUT` failing leaves it `completed` with no Resolution; a re-delivery then appends exactly one), and the exported GoDoc no longer documents a `resolver` parameter and a path walk this port removed.

## v0.19.0

- fix: **a task created after the controller started is added to the identifier→path index, so its later commands stop re-walking the whole vault.** A trigger-only controller (`POLL_INTERVAL=0s`) builds the index once at pod start and nothing added a file created afterwards, so every result and frontmatter command for such a task walked all ~17,000 files over git-rest. Measured 2026-10-25 on prod `agent-task-controller-openclaw-0` (`v0.18.3`): 155 of 159 walked identifiers were created after pod start, each walked ~14 times; walk time reached 1,600–2,000 s per hour, the single-threaded consumer fell 60 minutes behind, and from 17:28Z commands were dropped as `command expired` — a PR-review create landed an hour late and blocked a merge. `TaskPathResolver` gains `Record`; the create-task executor records the path it wrote when the index reports a clean miss, and `FindTaskFilePath` records the single file a walk matched. `Record` never replaces an entry holding two or more paths, so a known duplicate stays an error. New log line `index: recorded <path> for task <id>` at `glog.V(2)`.
- feat: **a command dropped as expired is now named and counted instead of vanishing.** The expiry predicate returns only a bool, so a dropped command left no record of which command was lost: the app-level filter logged the expire/now pair at `V(2)` without the command, and the library-level `CommandExpiredError` path logged at Warning only when its sampler fired and never named the task. `libkafka.NewMessageHandlerBatchFilter` has nowhere to report a drop, so `newCommandHandler` now composes `command.NewExpiredCommandBatchHandler` instead — the same partition-and-forward behaviour, plus a per-drop call to a new `command.ExpiredCommandObserver`. `command.NewLoggingExpiredCommandObserver` logs every drop unconditionally with `requestID`, `operation`, `requestTime` and the topic/partition/offset, and increments `agent_controller_commands_expired_total{operation}`, pre-initialised over the five operations this controller consumes so every series reads 0 before the first drop. The predicate `NewExpiredCommandSkip` is unchanged and stays pure and context-free: the observer sits in the wrapper beside it, because the filter contract forbids side effects inside `skip` and `skip` receives no context. No result object is written for a dropped command — an expired command is usually a create-task with no task file yet, so a write would land as `not_found` noise on the series `AgentControllerResultNotFound` alerts on.

## v0.18.4

- fix: **the command consumer no longer replays the whole retained request topic on every restart, and an expired batch no longer opens a transaction at all.** A process with no committed offset resolved to `offset(oldest)` — `cdb.RunCommandConsumerTx` hardcodes `NewStoreOffsetManager(..., OffsetOldest, ...)` — so each restart began at the oldest retained message and discarded everything older than the 60-minute `commandExpireDuration` on arrival. Measured on prod `agent-task-controller-openclaw-0` (`v0.18.2`): `consumer group offsets … map[0:oldest]` beside `trigger offsets map[0:424026]`, `offset(oldest) started`, `lag: 67107`, and a drain rate of 17.85 msg/s — ~53 minutes of replay before the first live command. The consumer is now composed by hand instead of through `RunCommandConsumerTx`, for two reasons. It starts from `libkafka.NewTTLSeekOffsetManager`, which on a store miss asks the broker for the first offset at or after `now − commandExpireDuration` and persists that resolution, so the start is the oldest command that can still execute rather than the oldest message that still exists; `InitialOffset` and `FallbackOffset` both report the newest offset so no recovery path can reinstate the replay. And `libkafka.NewMessageHandlerBatchFilter` composed outside `cdb.CreateCommandMessageHandlerBatch` drops a command whose `RequestTime` is already past the window before the batch reaches `NewMessageHandlerBatchTxUpdate`, so a batch whose commands have all expired — the shape every replayed batch takes — opens no handler transaction at all (the single offset commit after the batch still writes), and a partly expired batch never carries the dead messages into one. The predicate is `pkg/command.NewExpiredCommandSkip`; it logs the drop at V(2) with the same wording the handler used, so moving the decision ahead of the transaction does not also silence it, and a payload that is not valid JSON is kept so a malformed message still reaches the handler's own error path. `COMMAND_BATCH_SIZE` is threaded through unchanged. `github.com/bborbe/kafka` moves to the release carrying both constructors. The fleet-wide `config.Consumer.Offsets.Initial` default is deliberately untouched: flipping it would change the start offset of every consumer in the fleet, and it was never the lever here — sarama reads that field only in its consumer-group session and in `partitionOffsetManager.NextOffset`, while this consumer passes an explicit offset to `ConsumePartition`.

## v0.18.3

- fix: **the command consumer shares one BoltDB transaction across a batch instead of paying one per message.** `CreateCommandConsumer` passed `libkafka.BatchSize(1)`, and the handler composition it feeds is already the batch-tx variant (`cdb.CreateCommandMessageHandlerBatch` → `NewMessageHandlerBatchTxUpdate` → `NewMessageHandlerBatchTx` → per-message `NewMessageHandlerTxSkipErrors`), so a batch size of 1 made every message open its own `db.Update` and fsync. The size is now the `COMMAND_BATCH_SIZE` argument (default 100), so a batch of N messages opens one handler transaction plus one offset transaction instead of N of each. Skip semantics are unchanged: the skip wrapper sits inside the batch, so an expired or failing message is logged and skipped without aborting the batch, and the offset still advances only after the whole batch commits. A new test pins the property: a batch of 100 expired messages, and a batch containing a malformed message, each perform exactly one `db.Update`.

## v0.18.2

- fix: **a trigger-only controller builds its identifier→path index at start, so a lookup stops paying the full directory walk.** The spec-016 index is published only at the end of a scan cycle, and `POLL_INTERVAL=0s` — the mode v0.18.0 added for a controller whose vault has another producer of change events — runs no cycle at all: the vault is scanned only on a trigger, and nothing in that deployment fires one. The index therefore stayed empty for the pod's whole life. Measured on prod `agent-task-controller-openclaw-0` (`v0.18.1`, 1 replica, 0 restarts, 17 h): `agent_controller_scan_cycles_total` 0 on all three results, 0 trigger fires, **0 index hits against 606 index misses**, and 605 of those misses walked the whole vault — `ListFiles(tasks/*.md)` plus one `ReadFile` per file over git-rest, 16,943 files, **median 18.3 s per lookup** (max 86.8 s). Because the command consumer is `BatchSize(1)`, that walk is a serial 18-second tax on every command: over the last 90 minutes of that window 234 walks consumed ~78 of 90 minutes, the consumer fell behind, and **85 commands were dropped as expired** against `commandExpireDuration = 60m` — a guaranteed expiry, not a race. `vaultScanner.Run` now calls a new `buildIndex` once before it starts waiting, and only in the trigger-only branch: one read-only pass over the task directory that lists, reads and parses each file's `task_identifier` and swaps the finished map in under the same write lock `publishIndex` uses, so a concurrent `Resolve` observes either the empty map or the complete one. It is deliberately narrower than `scanFiles` — no `Pull`, no `auto-inject` repair of a missing identifier, no write, no commit, no changed-task publish — so a trigger-only deployment keeps the property that made `POLL_INTERVAL=0s` right in the first place (the scanner writes nothing and republishes no vault's full task set as changed on every restart), and it leaves the `hashes` bookkeeping untouched so a later cycle's change detection is unchanged. A file without a valid `task_identifier` is skipped rather than repaired: the index is a lookup cache, the walk stays the recovery, and a file created after the pass still misses and falls back exactly as before. The pass costs the same single walk it replaces (16,943 reads, once per pod start) and turns every later lookup for a file that already existed into one read. No new config surface, env var, CLI flag or metric; the one addition to the log is `buildIndex: <n> identifier(s) from <n> file(s) in <dur> (<n> skipped)` at `glog.V(2)` — the deployed verbosity — so a deployed controller's index size is readable rather than inferred.

## v0.18.1

- fix: **the startup git-rest readiness probe retries with bounded backoff instead of exiting 1 on the first refusal.** Observed 2026-10-23T10:56:01Z on nuke dev: pod `agent-task-controller-openclaw-0` rolled out, probed `/readiness` 25 ms after "application started", got `connect: connection refused` from `vault-obsidian-openclaw:9090`, and exited 1. The vault pod was healthy throughout (`restartCount=0`, ready since 2026-10-22T17:36:49Z), so the refusal was a transient of pod creation that would have cleared on its own — but each exit spent a Sentry event (issue NUKE-DEV-EX, 7 events over 92 days) and left the controller dispatching nothing until its next restart. `EnsureCloned` now makes 5 attempts with 2s/4s/8s/16s backoff, each attempt capped at 2 s so a blackholed endpoint cannot stretch a single attempt to the HTTP client's 30 s. Every refused attempt logs a WARNING quoting the attempt number and the failure, and a probe that never succeeds still fails the process after ~40 s — inside the liveness probe's ~50 s kill window, which binds because the router and `/healthz` are only built after `EnsureCloned` returns.

## v0.18.0

- feat: **a non-positive `POLL_INTERVAL` disables the periodic vault scan, leaving it trigger-only.** `time.NewTicker` panics on a non-positive duration, so no ticker is constructed at all and the nil channel blocks forever; the scan then runs only when something sends on the trigger. This is the mode a controller needs when another writer is the sole producer of change events and its per-pass read of every task file — 8,573 files per pass on the personal vault — is pure cost.

## v0.17.0

- fix: **a task pinned to another cluster is published instead of dropped.** The controller skipped a task whose `cluster:` frontmatter named a different cluster, but the task topic keeps only the latest event per task: dropping the pinned version left the executor's view on the last version this controller had published, often an untagged one from before the operator pinned the task, so the executor kept running a task pinned elsewhere. Observed 2026-10-23: task `a2b59b2e` pinned `cluster: sun` ran twice on nuke prod. Every changed task is now published with its pin intact, and executors — which already filter by cluster — make the routing decision. The `CLUSTER` and `PUBLISH_UNTAGGED` settings and the `skipped_foreign_cluster` publish label are removed; untagged tasks are published exactly as before.

## v0.16.2

- fix: **a transient Kafka consume error no longer terminates the controller process.** The command consumer returned its transport error to `service.Run`, which treats it as fatal, so a single `kafka: error while consuming <topic>/<partition>: EOF` exited the binary and Kubernetes restarted it — measured 2026-10-22: **six restarts in 5h31m**, each preceded by a consume EOF at a request-topic lag of 257–265. While the controller is down or behind it scans nothing and publishes nothing, so every in-flight task command waits out the restart and the topic then drains one message at a time (~3.4 s each). `CreateCommandConsumer` now wraps the consumer in `RetryConsumer`, which logs the error and re-enters after 5 s until the context ends; a shutdown returns nil rather than an error. Covered by three cases: clean return stops after one call, a transient error re-enters until it succeeds, and a context cancelled during the wait returns nil without propagating.

## v0.16.1

- fix: **an agent's result write can no longer change a task's `cluster:` pin.** `MergeFrontmatter` overlaid every incoming key, and `cluster` belonged to no ownership guard, so a result built from the spawn-time task snapshot echoed the snapshot's `cluster` back onto the task. Measured 2026-10-21: an operator removed `cluster: sun` from a running pr-reviewer task and the job's result write six minutes later restored it; 27 tasks were re-tagged this way onto a cluster being shut down. `cluster` is now operator-pinned: the on-disk value always wins, an incoming value can never introduce the key when it is absent on disk, and every discarded incoming value is logged on the `ownership guard kept on-disk` line.

## v0.16.0

- fix: **an unchanged result write no longer posts to git-rest.** `AtomicReadModifyWriteAndCommitPush` POSTed the merged content even when the modify closure returned the bytes it read — e.g. a re-delivered result, or one where the ownership guard keeps every on-disk field. Each POST is a git-rest write+commit+push round trip, measured 2026-10-21 on openclaw-0 at p50 2.71 s / p99 7.18 s over 1294 writes, and it dominated per-message intake time (p50 2.40 s/msg under a 1172-deep backlog, 20 `command expired` drops). An unchanged result now returns without the POST and logs `gitrest: skip unchanged read-modify-write` at V(2).
- feat: intake timing is visible at the deployed `-v=2`. `WriteResult: completed successfully` now carries the write duration in ms, a plain resolver miss logs `FindTaskFilePath: index miss`, and the three index-hit fallback reasons (unreadable, invalid frontmatter, identifier no longer carried) moved from V(3) to V(2).

## v0.15.1

- fix: **the `github-update-go` supersede hook actually fires.** `listUpdateGoCandidateTitles` built its candidate glob from the repo slug alone (`tasks/<owner>-<repo> *.md`), dropping the `Update Go ` title prefix the emitted files carry — so `ListFiles` matched nothing, the scan exited silently, and the v0.13.0 collapse never aborted a single task. Measured 2026-10-21: 0 of 1552 update-go task files carried `superseded_by`, and six repos received creates after the v0.14.0 deploy with no supersede written. The glob is now built from the same prefix the in-memory filter uses, and a regression test applies real glob semantics over emitter-shaped filenames so a prefix-less glob fails instead of returning an empty slice.
- fix: **the update-go look-back budget bounds aborts, not reads.** `SUPERSEDE_LOOKBACK` (default 7) was spent on every candidate file the scan read, including already-closed rows, and filenames end in a commit SHA so listing order is not recency order. A repo carries up to 66 historical update-go files, so a create could burn the whole budget on closed rows and abort none of the open excess the hook exists to collapse — a defect that only became reachable once the glob above started matching. The budget now counts still-open priors only, so the scan reads until it has found `k` of them; reads stay bounded by the repo's own file count (66 measured, 2026-10-21).
- fix: **superseding an update-go task no longer rewrites its attribution.** Both supersede hooks shared `transitionPrior`, which stamps `created_by: recurring-task-creator` and a "prior recurring task" commit message — truthful for a prior the recurring publisher emitted, false for a `github-update-go` task the update-go watcher emitted. Unreachable before the glob fix above; the sibling build-fix retire path already omitted the field for this reason. `transitionPrior` now takes the commit-message prefix and a `setCreatedBy` flag, and the update-go hook passes `false`, so the four frozen fields (`status`, `phase`, `completed_date`, `superseded_by`) are written and the prior's real `created_by` survives. Covered by a spec that executes the modify closure and asserts the prior's `created_by` is preserved.

## v0.14.0

- feat: **a controller publishes only the tasks that belong to its cluster.** The new optional `CLUSTER` env names the cluster this controller runs in. A task whose `cluster:` frontmatter names a different cluster is not published, and is counted as `agent_controller_tasks_published_total{outcome="skipped_foreign_cluster"}`. A task without `cluster:` is published only when `PUBLISH_UNTAGGED` is true (the default); set it false on a cluster that runs only explicitly tagged tasks, such as sun. If `CLUSTER` is empty, every task is published as before. Deletes are always published.

## v0.13.0

- feat: collapse the `github-update-go` queue to one open task per repo. The watcher's `openUpdatePRGate` drops a repo with an open update **PR** from the emit cycle, but nothing guarded the **task** side, so a repo that never reached a PR accumulated one task per commit — measured 2026-10-20: 309 open update-go tasks across 68 repos, 217 of them excess, with `bborbe/agent-claude` alone holding 28. After a new update task is materialized, every other still-open update task for the same repo is transitioned to `aborted` with a `superseded_by` back-pointer to the new one, capped at `SupersedeLookback` candidates exactly as the recurring-task path is. Candidates are matched on the parsed `repo` and `task_type` frontmatter rather than on the filename alone, so a file that merely looks like an update task is never aborted, and `github-update-go-decision` rows — operator questions that never start a job — are never touched.

## v0.11.5

- fix: an agent-to-agent handoff can now change the routing `assignee`. ## v0.6.6

- fix: recover task results lost to git-rest pull lag — `WriteResult` now retries the task-file lookup up to 3 times with a 1s pause before giving up, instead of dropping the result on the first miss. The controller lists files over git-rest's HTTP API rather than a local clone, and git-rest pulls on a timer, so a result can arrive before the file it belongs to is visible; that result was previously discarded permanently (warning + `results_written{result="not_found"}` + `nil`, so the Kafka offset advanced regardless). The retry is deliberately in-process rather than an error return: the consumer runs `SkipCorruptBatches:false` on an offset consumer, so erroring on a permanently-missing file (deleted or renamed task) would block the partition and halt the controller. Give-up behaviour and the `not_found` label are unchanged, so the `AgentControllerResultNotFound` alert keeps working. A recovery logs `task file for identifier X resolved on attempt N of 3` unconditionally — the only signal separating transient lag from permanent loss, and what the alert's provisional threshold should be tuned from.
