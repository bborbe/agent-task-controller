## Summary

- The vault scanner's `task_identifier` backfill is a self-healing repair path with no termination condition. It assumes that performing a write clears the condition that triggered the write, and nothing verifies that assumption.
- This spec adds a **convergence guard**: before a repair write is persisted, the scanner re-evaluates the repair trigger against the exact bytes it is about to write, using the same parse pipeline the next scan cycle would use. If the trigger is still live, the write is refused entirely, an ERROR is logged, and a skip counter increments.
- The guard is root-cause-agnostic. It bounds any non-converging repair, including causes nobody has enumerated. `bug-task-identifier-non-uuid-loop` fixes the one trigger that is known today; this spec makes the next unknown trigger cost one log line instead of a 50-hour outage.
- The guard is exercised by a **real** input where one can be found, not a test double. The block-style `task_identifier` value originally chosen for that role no longer qualifies: `bug-task-identifier-non-uuid-loop` ships span-aware removal, which strips block sequences, block mappings, and block scalars cleanly, so all three converge. AC2's fixture must be substituted and the substitution declared in the PR (see Constraints).
- The halt is keyed on the file's on-disk content hash, so it re-arms automatically and exactly once per distinct file state, and it never leaks an empty task identifier into the deleted-tasks stream.

## Problem

Any self-healing write path that re-evaluates its own trigger on the next cycle is a latent infinite loop unless something verifies that the write cleared the trigger. The vault scanner has three such repair sites and no such verification. This is a structural gap, not a coding slip: spec 001 reasoned carefully about *which replica is allowed to mint* an identifier and gated it behind `AUTO_INJECT_TASK_IDENTIFIER`, but the question *does minting terminate* was never asked. Ten weeks later the loop arrived through a door spec 001 had not modelled — a malformed frontmatter value that routed a key-present file into the key-absent branch — and one replica minting forever proved exactly as damaging as two replicas racing would have been. Fixing the specific misrouted value closes that door. It does not answer the question spec 001 left open, and the cost of leaving it open is unbounded writes to a shared git repository that many other systems read.

## Goal

No task file is ever rewritten more than once for the same unrepaired condition. Before any `task_identifier` repair write reaches the vault, the scanner proves against the candidate bytes that the write will clear its own trigger; a write that would not is refused, leaves zero footprint, and surfaces to the operator as an ERROR log plus a metric. A halted file re-arms by itself when its content changes on disk, and halt bookkeeping never emits an empty task identifier downstream.

## Non-goals

- Do NOT re-implement the type-and-validity fix — that ships in `bug-task-identifier-non-uuid-loop` and must land first.
- Do NOT make the convergence guard configurable, opt-outable, or threshold-tunable — invariant; an escape hatch on a termination guard is the regression itself. If a future consumer demands variation, that is a separate spec.
- Do NOT add a per-file write-rate circuit breaker (e.g. "max N writes per file per hour") — a rate limit slows an infinite loop; the guard stops it. If a rate limit is wanted later as defense in depth, that is a separate spec.
- Do NOT add commit-rate anomaly alerting on the vault repo — separate concern, separate spec, different owner (monitoring config lives in `bborbe/quant`).
- Do NOT redesign or reinstate the removed `AgentControllerWritebackFailing` alert — out of scope; tracked separately.
- Do NOT attempt to identify what originally wrote `task_identifier: 501` — open question, tracked separately. One plausible lead is `IncrementFrontmatterCommand` (`pkg/command/task_increment_frontmatter_executor.go`), which performs an atomic `+N` on a NUMERIC frontmatter key and would write an unquoted integer if it were ever misrouted to `task_identifier`. **This is UNVERIFIED** — no evidence links it to the write, and this spec must not be implemented as if it were the cause. The guard must hold regardless of origin.
- Do NOT change `DeduplicateFrontmatter`'s last-wins semantics — other callers depend on it, and the guard's correctness depends on modelling it faithfully rather than changing it.
- Do NOT change `AUTO_INJECT_TASK_IDENTIFIER` semantics from spec 001 — when the flag is `false`, no repair is attempted, so the guard must not fire.
- Do NOT publish a task whose `task_identifier` repair was halted — a file with no valid identifier is not publishable, same as today.
- Do NOT introduce a new Prometheus counter — the new reason joins the existing closed `SkipReason` set so operators keep watching one series.

## Desired Behavior

1. Before any repair write is persisted, the scanner re-evaluates the repair trigger against the exact bytes it is about to write, using the same parse pipeline the next scan cycle would use: frontmatter extraction, duplicate-key deduplication, and YAML unmarshal. The write proceeds only when the re-evaluated `task_identifier` is present, is a string, and equals the freshly minted UUID.
2. When that re-evaluation shows the trigger is still live — including when the candidate bytes fail to parse at all — the write is refused entirely (nothing written, nothing committed), an ERROR log is emitted containing the frozen substring `task_identifier repair did not converge, halting repair for:` plus the file path, and the skip counter increments once on the reason label `repair_not_converging`. This behavior is root-cause-agnostic: it halts any repair that fails to converge, including causes not anticipated by this spec.
3. A halted file is remembered by its on-disk content hash, so subsequent scan cycles neither re-attempt the repair nor re-log nor re-count while the file is unchanged. When the file's content changes on disk — an operator edit or any other writer — the repair is attempted once more from scratch. Bookkeeping for a halted file never emits an empty task identifier into the deleted-tasks stream when the file is later removed.

## Design Decisions

- **Guard before the write, not after.** Re-evaluating the candidate bytes in memory and refusing to persist means a non-converging repair leaves zero footprint in the vault. Writing first and checking afterwards would still commit one bad file per detection and still push it to a shared repo.
- **Guard keyed on the same parse pipeline the next cycle uses.** The incident happened precisely because the write path and the read path disagreed about what the file says. Reusing the read path's exact pipeline — including `DeduplicateFrontmatter`'s last-wins semantics — is what makes the guard catch the accumulator shape: post-injection, the deduped view resolves `task_identifier` to the stale value, not to the minted UUID.
- **A parse failure inside the guard is non-convergence, not an error to swallow.** Fail-closed. Candidate bytes that do not parse cannot be proven to have cleared the trigger, so they are refused.
- **Halt keyed on content hash, not a retry counter.** A counter would need tuning and would still eventually give up on a file that a later operator edit made repairable. Hashing re-arms automatically and exactly once per distinct file state, and it reuses the `v.hashes` bookkeeping the scanner already maintains.
- **The counter is an edge, and the metric documentation moves to match — not the other way round.** The obvious alternative was to make `repair_not_converging` increment once per cycle like every sibling label, preserving the existing `Help` contract and letting detection stay `rate(...) > 0`. **The code rules that out.** `processFile` short-circuits at `pkg/scanner/vault_scanner.go:238-241` — `hash := sha256.Sum256(content)` followed by `if existing, ok := v.hashes[relPath]; ok && existing.hash == hash { return ... }` — so an unchanged file never reaches the repair path at all on subsequent cycles. Hash-keyed halt bookkeeping stores the file's real content hash and therefore rides that existing short-circuit for free, which is what gives DB3 its self-clearing behavior. Incrementing per cycle would require deliberately bypassing the scanner's core hash gate purely to bump a counter — a larger and riskier change than editing a `Help` string. The consequences are accepted and reconciled in Failure Modes: detection for this one label is `increase(agent_controller_vault_scanner_skipped_files_total{reason="repair_not_converging"}[6h]) > 0`, not `rate(...) > 0`, and a level check `> 0` is rejected because it survives forever after the file is repaired and resets on pod restart. AC7 makes updating the `Help` string a hard requirement so no operator is misled by a stale contract.
- **Reason label added to the existing closed skip-reason set** rather than a new counter — the repo's established convention (`AvailableSkipReasons` with zero pre-initialisation) already gives operators one place to watch, and a new series would have to be discovered separately.

## Constraints

- **This spec depends on `bug-task-identifier-non-uuid-loop` having landed.** The guard sits on the strip-and-reinject path that spec corrects; without it, the block-style fixture never reaches the repair path (it lands on the key-absent branch instead) and AC2 is unreachable.
- **AC2's block-style fixture is dead on arrival and must be substituted.** This is no longer conditional. `bug-task-identifier-non-uuid-loop` now makes span-aware removal a hard constraint — the key line **and every following frontmatter line more indented than it** are deleted — so `  - a` / `  - b` (and a block mapping, and a block scalar) are stripped cleanly and all three converge in one write. The block-style non-convergence AC2 was written around does not exist after that spec lands. The implementer must substitute a seam-free non-converging input verified against the **shipped** `removeTaskIdentifier`, or, failing that, a synthetic fault-injection seam, and must state in the PR which fixture was used and why. Adopting a seam means AC2's production-reachability claim is not proven — say so in the PR rather than silently swapping. Every other part of AC2's evidence (zero writes, byte-identical on-disk file, exactly one ERROR log across five cycles, counter +1, zero `ScanResult.Changed` entries) is unchanged and applies to whichever fixture is chosen.
- `DeduplicateFrontmatter`'s last-wins semantics are frozen — other callers depend on it, and the guard's correctness depends on modelling it faithfully.
- Spec 001's `AUTO_INJECT_TASK_IDENTIFIER` gate is frozen: when `false`, no repair is attempted and the guard must not fire (AC5 row ii). The frozen substring `AUTO_INJECT_TASK_IDENTIFIER=false; skipping task without valid task_identifier:` is unchanged.
- The existing `(nil, "", false)` skip return shape and `(nil, relPath, false)` write return shape from `processFile` are frozen — downstream `scanFiles` bookkeeping depends on them and must not need changes. A halt returns the skip shape.
- `SkipReason` is a closed set with zero pre-initialisation in `init()`; the new reason must be added to `AvailableSkipReasons` so the series exists at 0 before the first halt (AC1).
- The `SkippedFilesTotal` `Help` string must be updated (AC7). Leaving it unchanged ships a metric whose documented contract is false for one of its labels.
- The content-hash short-circuit at `pkg/scanner/vault_scanner.go:238-241` is frozen — the halt rides it rather than replacing it.
- The zero-hash sentinel stored by `injectAndStore` on a successful write (`hash: [32]byte{}`) is frozen — a halt stores the file's real content hash instead, which is exactly what makes the two paths behave differently on the next cycle.
- `bug-task-identifier-non-uuid-loop` AC2 rows 10-12 must **not** be changed by this spec's prompt (AC6). Under that spec's span-aware removal they converge at write count `1` with valid post-write frontmatter, so their expectations are already correct post-guard; this spec's prompt only proves the guard stays silent on them.

## Security / Abuse Cases

The scanner parses operator- and agent-authored Markdown from a shared git repository, so frontmatter is untrusted input.

- **What an attacker (or a buggy writer) controls:** the entire YAML frontmatter of any task file. Without the guard, a single crafted value is an unbounded write amplifier against a shared git repository — a self-inflicted denial of service on the vault, demonstrated at 3007 writes to one file. The guard reduces the worst case for any single crafted file to zero writes plus one log line per distinct content state.
- **What crosses a trust boundary:** the scanner's writes are committed and pushed to a repository other systems read. Refusing to persist a non-converging repair keeps malformed input from becoming committed state at all, rather than committing it and cleaning up afterwards.
- **What can hang or retry forever:** the repair loop. The guard is unconditional and has no opt-out, which is why the Non-goals reject making it configurable — a flag that disables a termination guard reintroduces exactly the failure the guard exists to prevent.
- **What must be validated:** the candidate bytes, before they are written, through the same pipeline the reader uses. Log lines must name the file path and never interpolate the raw offending value, so a large sequence or mapping under `task_identifier` cannot be used to flood the log.

## Do-Nothing Option

`bug-task-identifier-non-uuid-loop` closes the one trigger that is known, and after it lands **there is no named pending instance of this failure.** That is the honest cost of this spec: it is bought on precedent, not on a live incident, and it will most likely never fire in production. Stating otherwise by reusing the 50-hour outage's numbers would be borrowing evidence that belongs to the other spec.

The precedent is the argument. This exact class has already recurred once. Spec 001 answered *who is allowed to mint an identifier* and gated it correctly behind a single-replica flag; it did not answer *does minting terminate*, and could not, because the question was never posed. Ten weeks later the loop returned through a different door — not a replica race, but a malformed value that routed a key-present file into the key-absent branch — and one replica minting forever cost as much as the race spec 001 prevented would have. The pattern is that a repair path is fixed for its known trigger, the structural gap stays open, and the next trigger arrives through a door nobody modelled. There are three such repair sites in `processFile` today, all of them writing to a shared git repository that many other systems read, and none of them verifies that its write cleared its trigger.

Doing nothing means the next unknown cause costs another unbounded rewrite loop, discovered the same way the last one was: by a human noticing the vault had become unusable. Doing this means it costs one ERROR log and one counter increment, and the guard does not need to know what the cause was. The change is one in-memory re-parse on a path that already parses the same bytes on the next cycle anyway, with no runtime cost on the healthy path, which never reaches it.
