## Summary

- The controller's result write-back merge is a shallow copy with the agent's payload applied second: every key that sits on no guard list is overwritten by the incoming value. That is correct for almost every key and wrong for cumulative counters.
- Two counters arrive this way, both from the agent's result payload and both landed by the controller's existing merge — no new writer: `metrics_agent_turns` (the agent's own turn count for the run, always emitted) and `metrics_interaction_count` (the run's human interaction count — emitted as `0` only when an unattended run can be evidenced, absent otherwise).
- This spec adds a **third behaviour** to the merge beside the two that exist (keep the on-disk value; incoming wins): **accumulate**. After N runs of one task, the on-disk total is the sum of the N per-run emitted values — never the latest run's value.
- Both obvious answers fail, and this spec rejects them in place: off the guard lists, incoming-wins overwrites a lifetime total with a single run's value (silent reset); on the controller-owned guard, the merge *discards* the emitted value (silent vanish — the failure mode the executor's own publisher documentation records verbatim for `trigger_count`).
- Nothing else moves: no new writer, no agent-side change, no edit to the guard lists, the terminal-`status` pin, the body merge, or the escalation dedup. Verified deterministically through the existing write-back test harness, then on dev and prod against real task runs.

## Problem

`metrics_interaction_count` is a cumulative lifetime counter, not a per-run measurement. 483 task files in the Personal vault carry it today (measured 2026-09-14 by `grep -rh '^metrics_interaction_count:' "25 Tasks/"`; 475 of them ≥ 10, 152 in the 11–38 band, range 0–1380, median 67). That measurement supersedes the older figure recorded on the vault decision page `Decide the Agent Interaction-Count Write Path` — "11–38 across 469" — and that vault page still needs the same correction. The agent half of this work will emit that key — and `metrics_agent_turns` beside it — inside the result payload, and the controller's write-back merges the payload into the task file with the incoming value winning for any key not on a guard list. The first agent run on a task that already carries a lifetime total therefore writes one run's number over the lifetime total, and reports success while doing it: no error, no log line, no failing test. The number the parent goal is built on ("how much work shipped without me this week?") is silently corrupted at its source, and the corruption is indistinguishable from a genuine low count. The same class of harm applies in the other direction — routing these keys onto the controller-owned guard makes the merge discard the emitted value instead, so the counter never moves at all. Neither existing behaviour is safe for these two keys, so accumulation has to exist as its own behaviour in the merge.

## Goal

The controller's result write-back merge treats `metrics_agent_turns` and `metrics_interaction_count` as cumulative counters: when the agent's payload carries a value and the task file already carries one, the written value is their sum; when the file carries none, the emitted value lands as the starting total; when the payload carries none, the file's value is left exactly as it was. After N runs of the same task the on-disk total equals the sum of the N per-run emitted values, every other frontmatter key keeps the behaviour it has today, and `docs/controller-design.md` states the rule as the third row of the Frontmatter Merge doctrine.

## Non-goals

- **Emitting the counts.** The payload half is the `agent` repo's work — spec `053-agent-result-interaction-count` (the vault task `Emit the Agent Interaction Count From the Job`), merged as `bborbe/agent` PR #69 and released as `v0.89.0`, with its fleet rollout still pending; this spec starts where a payload carrying the keys already arrives.
- **Backfilling existing tasks.** The 483 files carrying `metrics_interaction_count` today keep their values; the accumulation starts from whatever is on disk at the first write-back after this ships.
- **The weekly rollup** that consumes the numbers.
- **Redefining `metrics_interaction_count`.** vault-cli v0.116.1 is the definition; this spec changes where a second contribution to the total comes from, not what the number means.
- **Exactly-once accumulation under Kafka redelivery.** No per-run identity exists on the payload today, so a re-delivered result is indistinguishable from a second run and would add its value twice. Named in Failure Modes with its detection and recovery; building a dedup key is a separate spec.
- **Any new knob.** No opt-out flag, no per-key allowlist, no configurable cap: an escape hatch that disables the accumulation would reintroduce the silent reset this spec exists to remove. Do NOT add one — invariant; if a future consumer demands variation, that is a separate spec.
- **Clamping or bounds-checking the counters.** The merge adds what it is given; it does not police the emitter's contract.

## Desired Behavior

1. **Both counter keys accumulate.** `metrics_agent_turns` and `metrics_interaction_count` are, and only these two are, cumulative in the merge: when the incoming payload carries a numeric value for one of them and the on-disk frontmatter carries a numeric value for the same key, the written value is their sum. No other key changes behaviour.
2. **An absent incoming key leaves the on-disk value exactly as it was.** The merge never deletes or zeroes these keys because the payload omitted them, and never writes `0` in place of a value. An emitted `0` (an evidenced unattended run) adds nothing to the total.
3. **An absent on-disk key takes the incoming value.** The first agent run on a task that never carried the counter writes the emitted value as the starting total.
4. **Numeric handling is value-based and panic-free.** `int`, `int64` and `float64` are compared and added by numeric value, so a JSON-decoded incoming `float64` adds correctly to a YAML-decoded on-disk `int`. If either side is non-numeric, the on-disk value is kept verbatim and the incoming value is discarded; when the two values differ, exactly one guard decision names the field, and when both sides hold the same non-numeric value the existing equal-values rule applies unchanged — zero decisions, because nothing was rejected. The merge never panics and never writes a value it could not compute. The comparison helper `frontmatterValueEqual` stays the comparison mechanism; `==` on two `any` values is never used, because it panics on two values holding the same uncomparable dynamic type and that panic would kill the single result-write chokepoint.
5. **Accumulation is a transform, not a guard discard.** A clean accumulation produces no guard decision and no new log line: the guard-decision vocabulary means "the on-disk value was kept and an incoming value rejected", which is not what accumulation does. The accumulated total in the written file is the evidence.
6. **Nothing else in the merge moves.** The guard lists keep exactly their current members (`trigger_count`, `retry_count`; `assignee`, `previous_assignee`); the terminal-`status` pin keeps pinning `status` without suppressing the accumulation of these counters, exactly as it already lets the agent's `phase` and result fields land; the body section merge, the preamble rules and the escalation-section dedup are untouched; every non-counter key still takes the incoming value on conflict.
7. **The doctrine doc and the changelog record the rule.** `docs/controller-design.md` § "Frontmatter Merge" gains the third row — the accumulated counters, their keys, and the reason they are neither controller-owned nor operator-owned — and `CHANGELOG.md` gains an `## Unreleased` bullet naming the change.

## Constraints

- **Single writer.** The Job never writes frontmatter; the controller's result write-back stays the only writer for these keys. Routing the counters through `IncrementFrontmatterCommand` / `UpdateFrontmatterCommand` is rejected and must stay rejected: `buildUpdateModifyFn` applies updates straight onto the on-disk frontmatter with no guard, making it a second writer by construction.
- **The guard lists are frozen** at `controllerOwnedFields = {trigger_count, retry_count}` and `operatorOwnedFields = {assignee, previous_assignee}`, with the terminal-`status` pin unchanged. Adding either counter key to `controllerOwnedFields` is the trap this spec exists to avoid: that guard discards rather than accumulates — the failure the executor's `PublishSetTriggerScope` interface doc records verbatim for `trigger_count` (`agent-task-executor`, `pkg/result_publisher.go`).
- **The two counter key names are a frozen cross-repo contract.** `metrics_agent_turns` and `metrics_interaction_count`, exactly these spellings — lowercase, snake_case, no alias, no version suffix. The emitter owns the names (spec `053-agent-result-interaction-count` in the `agent` repo, the vault task `Emit the Agent Interaction Count From the Job`); this spec consumes them and renames nothing. A renamed emitter key is a silent no-op here — see Failure Modes.
- **Release ordering across the two repos.** The controller change must reach dev and prod **before** the emitter's rollout reaches the Job fleet. The emitter's library release is already cut (`agent` `v0.89.0`); its rollout — the `agent-claude` image built on it plus the three `nuke/agent` pins — is pending as of 2026-09-14. The window in which the emitter is live and this fix is not is exactly the silent-reset window this spec closes, and the Rung-2/Rung-3 preconditions enforce the order at verification time.
- **`frontmatterValueEqual` remains the comparison mechanism** — never `==` on two `any` values.
- **The merge keeps exactly one call site**: the result write-back path. No new call site, no new exported entry point.
- **No new log line, no new metric, no new config field, no new flag.**
- The existing guard-list semantics, the operator-owned `assignee` empty-clear exception, the terminal pin, the body merge and the escalation dedup keep their current behaviour; their existing specs pass unmodified.
- The write stays inside the existing atomic read-modify-write-and-commit-push primitive; no new write path.

## Security / Abuse Cases

- **What an attacker (or a buggy emitter) controls:** the entire incoming frontmatter map of the result payload — arbitrary keys, arbitrary value types, arbitrary numbers. The merge must treat every incoming value as untrusted: no panic on any type (`frontmatterValueEqual`'s `reflect.DeepEqual` fallback), no write of a value that could not be computed, no type assertion that can fail hard.
- **Trust boundary crossed:** Kafka (`agent-task-v1-request`) → controller → the vault git repo. The controller is the only component with write authority; the payload crosses the boundary as data and must never be treated as an instruction to write a key outside the accumulation rule.
- **Unbounded growth:** a payload can inflate a counter without limit. The merge adds what it is given and clamps nothing (a measurement, not a control input); the emitter's contract bounds it per run. An operator notices through the rollup and corrects by hand.
- **What must be validated:** non-numeric values on either side (kept verbatim, one decision when the values differ and none when they are equal, no panic); absent keys (never deleted, never zeroed); the numeric conversion path (int / int64 / float64 only — a `map` or `slice` value must fall to the keep-verbatim branch, never to an arithmetic path).
- **What can hang or retry forever:** the git-rest write retry, which blocks the consumer goroutine and holds the offset — bounded by git-rest recovery, and visible through the readiness endpoint. The merge itself has no loop, no timeout and no network call.
- **What can race:** two writers on one file. The vault is partitioned by `target_vault` routing so exactly one controller writes a given file, and the controller's atomic read-modify-write runs under a mutex — accumulation is therefore not racing a second controller, but it is not idempotent under redelivery (see Failure Modes).

## Do-Nothing Option

The current approach is acceptable only while nothing emits these keys — and the emitter is no longer hypothetical: it is merged (`bborbe/agent` PR #69, 2026-09-14) and released (`v0.89.0`), with only its fleet rollout pending. The moment that rollout lands before this fix does, the first agent run on any task carrying an existing `metrics_interaction_count` overwrites a lifetime total with a single run's value, and the merge reports success. The vault's numbers then drift downward silently, task by task, and the rollup built on them measures the drift as a drop in work. Doing nothing here does not leave the system as it is; it arms the corruption for the other half's rollout, which is already queued.
