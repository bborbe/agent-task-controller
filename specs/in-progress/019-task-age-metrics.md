## Summary

- Two new Prometheus series report, per controller vault, how long the oldest non-terminal task record has been non-terminal (in seconds) and how many non-terminal records fall into `lt_1d` / `1d_7d` / `gt_7d` / `undated`.
- Both are levels, recomputed by a **dedicated ticker** that runs even when `POLL_INTERVAL=0s` — the mode the three nuke-prod controllers were observed running on 2026-10-28 (`CHANGELOG.md` v0.22.6), where the existing scan-cycle gauge is dead. The cadence is a fixed 60-second package constant, not configuration.
- Non-terminal means `status` is neither `completed` nor `aborted`. Age is taken from `created`, then `created_date`, then `queued_at`, then `job_started_at`; the first **parseable** value wins, a record carrying none of them is counted in `undated` rather than guessed at, and a future timestamp clamps to 0.
- The `vault` label carries the controller's own configured `VAULT_NAME` (`openclaw`), so the dashboard selector that already matches `openclaw|private-agent` needs no change.
- Go change plus the metric contract written into `docs/controller-design.md` and one `## Unreleased` `CHANGELOG.md` bullet. The alert rule, the dashboard panel, the chart tag bump and the dev/prod deploy stay the task's own steps.

## Problem

The operator's rule — "keeping a task until forever is a bug" — has no instrument behind it. Nothing in the controller, on the dashboard or in any alert reports how old the oldest non-terminal record is. A board with 31 non-terminal records is read by hand, and a hand read cannot distinguish a record two hours old from one nineteen days old without opening every file.

The obvious place to hang such a gauge is next to the existing `agent_controller_update_go_stuck_planning_tasks`, which is `Set` at the end of `scanFiles`. That placement is a trap: the three nuke-prod controllers observed on 2026-10-28 (`CHANGELOG.md` v0.22.6) each run `pollInterval: "0s"`, so `Run` constructs no ticker and `scanFiles` only ever runs on a trigger that nothing fires in those deployments. A gauge added there would be dead in exactly the deployment it was written for — the same dead-on-prod shape this repo's own `CHANGELOG.md` records in its **v0.22.6** entry, where the capped-and-idle sweep added in v0.22.5 hung off `scanFiles` and never executed on a trigger-only controller. An age cannot advance on a change event anyway; it advances with the wall clock, so it needs a clock-driven recompute.

The second half of the gap is definitional: "non-terminal" and "age" are not written down anywhere the code can follow. Without a frozen precedence, a record dated only by `queued_at` is indistinguishable from an undated one, and the instrument reports a number nobody can reconcile.

## Goal

After this work:

- A running controller publishes `agent_controller_task_oldest_age_seconds{vault="<its VAULT_NAME>"}` and four `agent_controller_task_age_bucket_tasks{vault="<its VAULT_NAME>",bucket="<one of lt_1d|1d_7d|gt_7d|undated>"}` series.
- The oldest-age value is the age in seconds of the oldest **dated** non-terminal record, recomputed on a path that runs under `POLL_INTERVAL=0s` at a fixed 60-second cadence that no configuration can change, and 0 when no dated non-terminal record exists.
- The four bucket series always exist after the first **successful** recompute, each reading 0 when its bucket is empty, and the oldest-age series falls back to 0 when the last dated record turns terminal.
- The recompute reads the vault and writes nothing: no git pull, no scan cycle, no vault write.
- The metric contract — names, label sets, bucket boundaries, age precedence and the 60-second cadence — is written in `docs/controller-design.md`, and the change carries a `## Unreleased` `CHANGELOG.md` entry.
- `make test` and `make precommit` are green, and every constructor call site in the repo compiles with the new parameters.

This spec delivers the instrument and its written contract only. It does not restate or satisfy the task page's SC1–SC5 as a whole — the task page is `/Users/bborbe/Documents/Obsidian/private-personal/25 Tasks/Nothing Measures How Long an Agent Record Has Been Non-Terminal.md` (outside this repo, so not machine-checkable): the live scrape, the `TaskAge` alert, the dashboard panel and the end-to-end record demonstration belong to the task's remaining subtasks, and the spec deliberately carries no Post-Deploy acceptance criterion.

## Non-goals

- **The `TaskAge` Alert CR, the dashboard panel, the chart values tag bump and the dev/prod deploy.** Those are subtasks 2 and 3 of that task page, and the deploy is a separate task-owned step. This spec changes no chart value and no `nuke/` file.
- **A release tag, and the release itself.** The `## Unreleased` bullet is in scope because this repo's established convention requires one — completed specs 006, 009, 012 and 013 each carry a CHANGELOG requirement, and `git log -- CHANGELOG.md` shows feature commits followed by `release vX.Y.Z` commits. Cutting the tag is not in scope. On merge to master the repo's own releaser turns `## Unreleased` into a version and publishes it (`.maintainer.yaml` sets `release.autoRelease: true`); dark-factory does not release this repo (`.dark-factory.yaml` sets `autoRelease: false`), so no release step belongs to a prompt.
- **A per-record series.** A series per task over ~19k files is a cardinality bomb; the aggregate is the design.
- **A second process, sweep or cron.** A separate reader of the same store would be a second counter to keep in step.
- **Any filter by assignee, phase or task type.** The series counts every non-terminal record, which is what makes the assigned-and-old records visible.
- **Changing the phase model, the terminal status set, or any existing record's status.** No record is closed or backfilled here.
- **A change to `agent_controller_update_go_stuck_planning_tasks` or to `scanFiles`.** The stuck-planning gauge keeps its current placement and meaning.
- **A new metric for unreadable or unparseable files.** Such a file is skipped; the existing skipped-files counter is a different signal and is not extended.
- **Any configuration knob at all** — no per-bucket threshold config, no enable/disable flag, no per-vault allowlist, and no interval setting: the recompute cadence is a package constant. Do NOT add one — invariant; if a future consumer demands variation, that is a separate spec.
- **Folding the age pass into the existing start-up index build.** The two passes stay separate even though they read the same files; coupling them would make the series depend on trigger-only mode.
- **The alert expression and the dashboard query.** `docs/controller-design.md` records the contract they consume; the rule and the panel live in `bborbe/nuke`.

## Desired Behavior

1. **Two level series, with frozen names and labels.** `agent_controller_task_oldest_age_seconds` is a gauge vector labelled `vault`, carrying the age in seconds of the oldest dated non-terminal record. `agent_controller_task_age_bucket_tasks` is a gauge vector labelled `vault` and `bucket`, carrying the number of non-terminal records in each bucket. The bucket label is a closed set of exactly four values: `lt_1d`, `1d_7d`, `gt_7d`, `undated`. Both are exposed through the metrics interface, implemented by the default implementation and by the regenerated fake, and both doc comments state that the value is a level rather than a counter — it falls back to 0 when the condition clears, which is what makes a threshold expression alertable. The oldest-age comment names the 7-day threshold in seconds (`604800`), because the rule that consumes it lives in another repository. The accessor method names and their parameter order are the implementer's choice at impl time; the metric names, the label names, the bucket values and the returned gauge type are frozen.

2. **Non-terminal is `status` neither `completed` nor `aborted`.** The status is read from the parsed frontmatter. A record whose status is empty or any other value is non-terminal, because it is not terminal. Frontmatter is deduplicated through the existing `DeduplicateFrontmatter` helper before it is unmarshalled, so a file whose duplicate keys deduplicate cleanly is not skipped: it is counted once, with the last value winning for each key, matching the doc sentence at `docs/controller-design.md:330`. A file whose content cannot be read, whose frontmatter cannot be extracted, whose frontmatter cannot be deduplicated or unmarshalled is skipped entirely — it lands in no bucket and never affects the oldest age — because a gauge must not be blanked by one broken file.

3. **Age precedence, first parseable value wins.** The age of a record is `now` minus the first of `created`, `created_date`, `queued_at`, `job_started_at` that parses. A value parses when it is RFC3339 (with or without fractional seconds) or a date-only `YYYY-MM-DD`, the latter read as midnight UTC — vault tooling writes both shapes, and treating a date-only value as unparseable would misclassify a dated record as undated. A value that is present but unparseable is skipped and the next field is tried. One clock read is taken per recompute and used for every record in that pass, so all ages in one pass are mutually consistent.

4. **A negative age is clamped to 0.** A record whose timestamp lies in the future yields an age of 0 rather than a negative number, and lands in `lt_1d`. The published value is whole seconds, truncated, and bucket classification uses that same truncated value, so the value a scrape reads and the bucket it lands in agree at the 24-hour and 7-day boundaries.

5. **Buckets are half-open where it matters, and every pass republishes the whole set.** `lt_1d` is strictly under 24 hours; `1d_7d` is 24 hours or more and 7 days or less; `gt_7d` is strictly over 7 days; `undated` is the count of non-terminal records with none of the four fields parseable. Classification uses the truncated whole-second age from DB4, so a record whose untruncated age is 7 days plus a fraction of a second publishes `604800` and lands in `1d_7d`, not in `gt_7d`. Every successful recompute `Set`s all four bucket series and the oldest-age series, including the empty ones, so the series exist and read 0 instead of disappearing from the scrape. Because the oldest age is a level, a pass in which the last dated record has turned terminal publishes 0 while the series stay present. A recompute that fails writes nothing, so the values from the previous successful pass stay.

6. **The oldest-age value is the maximum over dated records, or 0.** The summary is computed from the path list, a single clock value and the configured vault name — the frozen input shape in Constraints — and published through the accessors, so it is exercisable in a unit spec without a configured scanner. With at least one dated non-terminal record, the value is the largest age among them. With none — an empty board, an all-terminal board, or an all-undated board — the value is 0, consistent with the level-falls-back-to-0 rule; the `undated` bucket is what keeps an all-undated board visible. The summary is a pure function of the files it reads and the clock value it is handed, so two consecutive passes over an unchanged board publish identical values: no value is accumulated, incremented or carried between passes.

7. **A dedicated ticker recomputes, independent of the poll interval.** `Run` constructs a second ticker from the scanner's metrics interval when that interval is positive, separate from the scan ticker and unaffected by a non-positive poll interval. When the metrics interval is positive it performs one recompute before entering the loop — so a fresh pod publishes all five series immediately rather than reporting "no data" for the first interval — and one recompute per tick. The recompute lists the task directory, reads and parses each file, and publishes through the summary with the configured vault name — it does not pull, does not scan, does not write, does not commit and sends nothing on the results channel. A non-positive metrics interval disables the whole metrics path: neither the start-up recompute nor the ticker is constructed, so the guard is uniform and the series are never published. That is also the guard against `time.NewTicker` panicking, matching the existing poll-interval convention at `pkg/scanner/vault_scanner.go:196-205`; configuration cannot produce the value, and only a caller can. Cancellation of the context returns `Run` promptly, and a long recompute is abandoned at the next file boundary when the context is done.

8. **The vault label is the controller's own configured name, and the interval is a constant.** Both constructors take the vault name and the metrics interval; the scanner stores both and uses the vault name verbatim as the `vault` label value. `main.go` passes its configured vault name and a package-level `metricsInterval` constant of 60 seconds. No environment variable, flag, chart value or other configuration surface sets the interval, so a deployed controller cannot widen or disable the cadence the task page `/Users/bborbe/Documents/Obsidian/private-personal/25 Tasks/Nothing Measures How Long an Agent Record Has Been Non-Terminal.md` pins at "at most 60 s", and no values change is needed; the controllers pick it up on their next image deploy. Every call site — `main.go`, the scanner's own specs and the command package's specs — is updated so the module builds.

9. **The contract is written down and the change is recorded.** `docs/controller-design.md` gains a `## Task Age Metrics` section stating the two series, their label sets, the four bucket boundaries, the four-field age precedence with the future clamp, the 60-second recompute, the single-writer rule and the reset-to-0 behaviour; that section is the contract the dashboard and the alert in `bborbe/nuke` consume. `CHANGELOG.md` gains a `## Unreleased` entry naming both series, because that is this repo's established convention — completed specs 006, 009, 012 and 013 each carry a CHANGELOG requirement, and `git log -- CHANGELOG.md` shows feature commits followed by `release vX.Y.Z` commits — and the repo's own releaser turns that section into a version on master.

## Constraints

- **Frozen metric names:** `agent_controller_task_oldest_age_seconds` and `agent_controller_task_age_bucket_tasks`. They are read by a dashboard query and an alert rule that live in `bborbe/nuke`; a rename breaks both silently.
- **Frozen label names and values:** labels `vault` and `bucket`; bucket values exactly `lt_1d`, `1d_7d`, `gt_7d`, `undated`. No record identifier, path or filename ever becomes a label value.
- **Frozen label value source:** the scanner's configured vault name, passed through verbatim. The vault-api display name (`private-agent`) is a different naming scheme and must not be applied — the dashboard selector already matches both spellings.
- **Frozen threshold arithmetic:** 7 days is `604800` seconds, and the bucket boundary is inclusive at 7 days for `1d_7d`, so the alert expression `age > 604800` and the `gt_7d` bucket select the same records. A `>=` would put a 7-day-old record in both `1d_7d` and the alert.
- **Frozen recompute interval:** a package-level `const metricsInterval = 60 * time.Second` in `main.go`, passed to the constructor. There is no `METRICS_INTERVAL` environment variable, no flag and no chart value: that task page pins "at most 60 s", and a knob that can widen or disable the cadence is an opt-out on the shipped behaviour. The constructor parameter stays because the specs need a short interval, and the scanner keeps its non-positive guard — no ticker and no start-up recompute — so a zero from a caller cannot panic `time.NewTicker`.
- **Frozen constructor signatures (wiring contract).** Both `NewVaultScanner` and `NewGitRestVaultScanner` take, in this order: the git client, the task directory, the poll interval, the trigger channel, the metrics implementation, the auto-inject flag, the vault name, and the metrics interval. Every call site and every spec depends on that order, and the wiring test records the last two arguments — a reordering is a cross-cutting break, not a local edit.
- **Frozen summary input shape (wiring contract).** The age summary takes the path list, one clock value and the vault name, in that order, and publishes through the metrics accessors. That shape is what lets a unit spec drive the four boundaries, the precedence, the maximum and the reset without a configured scanner, so it is fixed for the same reason the metric names are.
- **The contract lives in the design doc.** `docs/controller-design.md` § Task Age Metrics is the cross-repo contract `bborbe/nuke`'s dashboard and alert consume — names, label sets, the four bucket boundaries, the four-field precedence and the 60-second cadence. A change to any of them is a cross-repo change and needs its own spec that updates that section in the same change.
- **Single writer:** the age series are written only by the metrics ticker. `scanFiles` must not also `Set` them — two writers would make the value depend on which path ran last, and the whole point of the ticker is that the scan path is dead in the trigger-only deployments observed on 2026-10-28. The v0.22.5/v0.22.6 shape recorded in `CHANGELOG.md` must not come back.
- **No vault writes from the recompute.** It uses the existing listing and read operations only.
- **A non-positive metrics interval is a caller-only guard, not a failure mode.** With an interval of 0 or less, neither the ticker nor the start-up recompute is constructed, mirroring the poll-interval guard at `pkg/scanner/vault_scanner.go:196-205` (`time.NewTicker` panics on a non-positive duration). Configuration cannot produce that value — `main.go` passes the 60-second constant — so only a caller, and only a spec, can; the guard exists so a zero from a caller cannot panic the process.
- **Existing behaviour untouched:** the stuck-planning gauge, its placement at the end of `scanFiles`, the scan cycle, the identifier index and the escalation paths are unchanged.
- **Single Go module; `make precommit` runs from the repo root.** The changed packages carry no Makefile.
- **The recompute runs inline in `Run`'s goroutine,** not in a second goroutine: concurrent readers of the same store are avoided, and a trigger arriving during a recompute waits in the buffered channel rather than being lost.

## Assumptions

- A deployed controller sets `VAULT_NAME` (it is a required setting today), so the `vault` label always has a value; there is no empty-label case to handle.
- The task directory listing returns every `.md` file in that directory, which is the same listing the scan cycle and the index build already rely on.
- Records on the board carry at least one of the four timestamp fields in most cases; the `undated` bucket exists for the remainder, and its count is the operator's signal that the frontmatter is not carrying a date.
- A 60-second full read of the board is affordable, and the cost is measured rather than assumed. The affordability proof is the repo's own equivalent pass: `buildIndex` (`pkg/scanner/vault_scanner.go:362-419`) performs the same list + read + parse work on every trigger-only start-up and logs its elapsed duration (`buildIndex: %d identifier(s) from %d file(s) in %v (%d skipped)`), so the real per-pass cost is readable from a deployed controller's log rather than estimated; the v0.22.6 `CHANGELOG.md` entry records that pass at **9139 identifiers on the three nuke-prod controllers, observed 2026-10-28**. The raw I/O floor is measured separately: on 2026-10-31, 19,362 `.md` files cost **2.49 s wall** (0.04 s user, 0.86 s sys) for a `find … -exec cat {} +` pass, and a re-count the same day read 19,365 files at 2.38 s wall — that is the I/O floor only, before any YAML parsing, not the whole cost. A 60-second cadence therefore costs one list + read + parse per minute, the same work the start-up index build already performs once per pod, and the ticker drops ticks rather than queueing them when a pass overruns.
- **Trigger-only mode is the deployed configuration, as observed rather than assumed:** the three nuke-prod controllers were each running `POLL_INTERVAL=0s` on 2026-10-28 immediately after the v0.22.5 apply (`CHANGELOG.md` v0.22.6, all three `1/1 Running`). This is a cross-repo runtime fact observed on that date, not a guarantee about every future deployment, and the design does not rest on it being universal: the dedicated ticker runs under both modes, and trigger-only is the mode where the existing scan-cycle gauge is dead and where the ticker is load-bearing.
- `testutil.ToFloat64` from the Prometheus client library is available for value assertions; it ships with the already-present module dependency (`client_golang`, and `client_model` is already a direct `go.mod` dependency, so the `dto.MetricType_GAUGE` import needs no `go.mod` edit). It is deliberately not used to prove presence, because the child series exists only once the accessor's `WithLabelValues` call has run.

## Failure Modes

| Trigger | Expected behavior | Recovery | Detection | Reversibility | Concurrency |
|---|---|---|---|---|---|
| The directory listing fails (git-rest error, vault unavailable) | The recompute is abandoned before any value is written; the previously published values stay in place and a warning is logged. Values are never `Set` to 0 on a failed read, because 0 would claim a clean board. On a pod's first recompute nothing has been published yet, so the series are absent until a successful pass | The next tick recomputes; the gauge is correct again within one interval | The warning line naming the failed listing; a frozen value across successive scrapes, or no series at all on a fresh pod | Reversible | The ticker runs in `Run`'s goroutine, so no second pass overlaps it |
| One file cannot be read or parsed | That file is skipped: it lands in no bucket and does not affect the oldest age; the pass completes for every other file | Automatic on the next successful read; a permanently broken file stays invisible in these series, which is the documented trade | The bucket counts sum to fewer than the number of non-terminal files; the age pass itself logs nothing | Reversible | N/A |
| The full read takes longer than the metrics interval | The ticker drops the missed ticks and the next recompute starts when the previous one returns; the value updates less often than the interval but never freezes permanently | The interval effectively becomes the read duration | The value's apparent cadence versus the fixed 60-second cadence | Reversible | Ticks are dropped, not queued, so no pile-up |
| A record's timestamp lies in the future (clock skew, hand-edited frontmatter) | The age clamps to 0 and the record lands in `lt_1d`; no negative value is published | Corrects itself when the clock catches up or the field is fixed | A record visibly absent from the expected bucket | Reversible | N/A |
| A record's timestamp is absurdly old (year 0001, a corrupted value) | The elapsed duration saturates at the maximum representable duration rather than overflowing, and the record lands in `gt_7d` | None needed for the instrument; the record itself is the operator's to fix | `gt_7d` rising without a corresponding old record | Reversible | N/A |
| The board holds only undated non-terminal records | The oldest-age value is 0 and `undated` equals the record count — the board is visible through the bucket, not through the age | None needed | A non-zero `undated` with a zero oldest age | Reversible | N/A |
| Two consecutive ticks fall across a record turning terminal | The pass is a point-in-time snapshot; a record terminal in the second pass leaves the bucket and the oldest age recomputes from what remains — 0 if it was the last dated record | Automatic on the next tick | The bucket count dropping by one, and the oldest age dropping to 0 | Reversible | N/A |
| Process clock jumps backwards | Ages shrink or clamp to 0 for the affected pass; no negative value is published | Corrects on the next pass after the clock settles | A sudden drop in the oldest age with no record closed | Reversible | N/A |
| Pod restart | The series are unpublished until the start-up recompute completes, then published from scratch | The start-up recompute | A scrape gap of one recompute duration | N/A | N/A |
| A trigger fires during a recompute | The trigger waits in the buffered channel and the scan cycle runs immediately afterwards; no trigger is lost | Automatic | The scan cycle's own log lines | N/A | Single goroutine: the recompute and the scan never run concurrently |

## Security / Abuse Cases

- **What can an attacker control?** Task frontmatter — `status` and the four timestamp fields — because agents and operators write those files. Every value is parsed defensively: an unparseable timestamp falls through to the next field and a value that parses but lies in the future clamps to 0. No file content reaches a log line, and no frontmatter value ever becomes a label, so a crafted value cannot create a series or flood the log.
- **What crosses a trust boundary?** Nothing new. The recompute is a read-only consumer of files the scanner already reads; it adds no HTTP endpoint, no Kafka message, no write path and no new credential.
- **What can hang or retry forever?** Nothing new: the recompute is a bounded loop over one listing with a context check per file, and it performs no retries. A slow store lengthens one pass and drops ticks rather than queueing them.
- **What is the label cardinality?** Bounded by construction: one `vault` value per process and a closed set of four bucket values, so at most five series per controller. Record identity is deliberately absent.
- **What must be validated?** The bucket label must come from the closed set, never from parsed content; the vault name must come from configuration, never from a file; and a non-positive interval must not reach `time.NewTicker`.

## Suggested Decomposition

**Size acknowledged:** 9 Desired Behaviors × 21 Acceptance Criteria (189) across 4 code layers — the metrics surface, the age summary, `Run`/ticker/wiring, and the docs — exceeds both the DB × AC > 50 and the > 3-layer thresholds. It stays one spec because the decomposition below gives every prompt a single independently verifiable outcome and no prompt spans more than two layers; splitting it would duplicate the frozen constructor-signature and summary-shape contracts across two specs.

| # | Prompt focus | Covers DBs | Covers ACs | Depends on |
|---|---|---|---|---|
| 1 | The metrics surface: both gauge vectors with their frozen names, labels and doc comments, the two interface accessors, the default implementations, the regenerated fake, and a `pkg/metrics` spec that gathers the registry and asserts both families, their gauge type and their exact label names | 1 | 2, 3 | — |
| 2 | The age summary: the non-terminal filter, the four-field precedence with date-only support and the negative clamp, the bucket classification, the maximum and the zero fallback, the skip-on-unreadable rule, plus the unit specs for the four boundaries, the four fields, the undated record, the terminal exclusion, the presence-through-Gather rule, the reset, the maximum, the idempotency, the skipped files, the cleanly-deduplicated duplicate keys and the future clamp | 2, 3, 4, 5, 6 | 4-11, 14-16 | prompt 1 (the summary writes through the accessors) |
| 3 | The periodic recompute and the wiring: the dedicated ticker with its start-up recompute and non-positive guard in `Run`, the `vaultName` and `metricsInterval` constructor parameters, the `metricsInterval` constant and the injectable construction helper in `main.go` (which takes the constructor as a parameter and is the only construction path), every call-site update, the ticker and vault-label specs, the wiring test that records the constructor arguments, and the negative-evidence specs that neither `RunCycle` nor `Run`'s start-up index build writes the age series | 7, 8 | 12, 13, 17, 18 | prompts 1-2 |

The DB column numbers the Desired Behavior entries; AC1 (`make test`) and AC21 (`make precommit`) are whole-repo gates satisfied once all four prompts have landed. Rationale: prompt 1 creates the series the rest writes through, so it comes first and is independently testable at the registry. Prompt 2 is pure computation over parsed files and needs no ticker, so it can be built and falsified entirely by unit specs. Prompt 3 is the only prompt that changes `Run`, the constructors and `main.go`, which is where every call site and the whole-repo build gate land — sequencing it last keeps the compile breakage confined to one prompt. Prompt 4 writes the contract and the release record from what prompts 1-2 built, and touches no code. The alert rule, the dashboard panel and the deploy are the task's own subtasks, not this spec's.

## Do-Nothing Option

Not acceptable. The gap is not theoretical: the board carried 31 non-terminal records at the 2026-10-31 read, and the only existing sweep reads assignment, not age, so an assigned record that sits open for weeks is invisible to every instrument the fleet has. The cheap-looking alternative — hang the gauge off the existing scan — would ship a series that is dead in the trigger-only deployments observed on 2026-10-28 while appearing solved in code review, which is worse than no series at all: it would take the pressure off the hand read without replacing it. The change is two gauges, one read-only pass and one ticker in code that already has a start-up full-read precedent, so there is no cheaper moment than before the alert and the panel are built on top of it.
