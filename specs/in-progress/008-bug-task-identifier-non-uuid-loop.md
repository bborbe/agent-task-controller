## Summary

- A task file whose frontmatter carries a `task_identifier` that is present but is **not a valid UUID string** sends the vault scanner into an unbounded rewrite loop: every scan cycle prepends a fresh UUID and never removes the offending key.
- Root cause is a silent Go type assertion at `pkg/scanner/vault_scanner.go:264`. `taskID, _ := fmMap["task_identifier"].(string)` discards the comma-ok result, so a non-string scalar (int, bool, null, float, sequence, mapping) yields `taskID == ""`. Line 266 (`if taskID == ""`) then routes to the **key-absent** branch — the one branch that passes RAW content to `injectAndStore` at line 275 without calling `removeTaskIdentifier`. The bad key survives every write.
- The same branch is reached by a value that IS a Go string but is empty or whitespace-only: `task_identifier: ""` asserts successfully to `""`, matches line 266, and takes the identical raw-content path. Quoting is **not** a reliable self-heal. `"501"` self-heals; `""`, `''`, and `"   "` loop exactly like the unquoted `501` did. Empty-quoted-string is in live use in this vault — the incident probe fixture itself writes `assignee: ""`.
- `DeduplicateFrontmatter` keeps the LAST value per key (`pkg/scanner/frontmatter.go`, `newContent[idx+1] = valNode`), so the trailing bad value wins on every subsequent scan and the loop never converges.
- Production, 2026-09-05: one task file with `task_identifier: 501` was rewritten every ~60s for 50 hours — 3007 appended UUID keys, a 163 KB task file, and ~317 MB of parser warnings that made `vault-cli task list` unusable across the entire vault. Stopped only by scaling the StatefulSet to 0.
- This spec ships the type-and-validity fix that closes the incident. The class fix — a convergence guard that refuses any repair write which does not clear its own trigger — ships separately in `scanner-repair-convergence-guard`.

## Problem

The vault scanner's `task_identifier` backfill is a self-healing repair path: observe a file whose identifier is missing or malformed, write a corrected file, move on. The parse site that decides which repair to apply collapses three distinguishable states — key absent, key present as a valid string, key present as something else — into two, and it does so silently by discarding a type assertion's error. The result is that a whole class of malformed values is misclassified as "absent" and handed to the one code path that deliberately does not strip anything, because in the genuine absent case there is nothing to strip. Every such write is committed and pushed through git-rest, so the damage is not local: it appends to a shared vault, grows the file without bound, and floods every downstream consumer that parses that vault. The blast radius of one malformed scalar in one task file was the entire vault's usability for 50 hours.

## Reproduction

### Production (2026-09-05, prod controller, `AUTO_INJECT_TASK_IDENTIFIER=true`)

Running image at incident time, verified live: `docker.prod.nuke.benjamin-borbe.de:443/bborbe/agent-task-controller:v0.7.1`. Repo master is at `v0.7.2`; neither carries a fix.

A task file in `24 Tasks/` carried the frontmatter key `task_identifier: 501` — an unquoted YAML integer.

1. Scanner reads the file. `extractFrontmatter` -> `DeduplicateFrontmatter` -> `yaml.Unmarshal` produces `fmMap["task_identifier"] = 501` (Go `int`).
2. `taskID, _ := fmMap["task_identifier"].(string)` (line 264) fails the assertion, discards the error with `_`, and yields `taskID == ""`.
3. `if taskID == ""` (line 266) matches. Because `autoInject` is `true`, control reaches `return v.injectAndStore(ctx, content, relPath, currentFMAssignee)` (line 275) — **RAW `content`**, no `removeTaskIdentifier` call.
4. `InjectTaskIdentifier` prepends `task_identifier: <fresh-uuid>` immediately after the opening `---`. The file now has TWO `task_identifier` keys: the new UUID first, `501` last.
5. `injectAndStore` stores the zero-hash sentinel (`hash: [32]byte{}`), so the next cycle re-processes the file rather than short-circuiting on the content hash at line 239.
6. Next cycle: `DeduplicateFrontmatter` keeps the LAST value per key, so the surviving value is `501` again. Goto 2.
7. Steady state after 50 hours at a ~60s poll: 3007 `task_identifier` keys in one file, 163 KB, one git-rest commit per cycle, ~317 MB of duplicate-key parser warnings emitted by downstream vault parsers. `vault-cli task list` became unusable vault-wide.
8. The loop was stopped by scaling the controller StatefulSet to 0. It does not self-terminate.

### The empty-string variant — byte-for-byte the same loop

`task_identifier: ""` is a YAML **string**. The type assertion at line 264 SUCCEEDS and yields `taskID == ""`. Line 266 matches for the same reason as the integer case, raw content goes to `injectAndStore` at line 275 without stripping, and dedup's last-wins keeps the trailing `""`. This is not an analogous failure — it is the identical failure through a different door. The same holds for `''` and for whitespace-only strings such as `"   "`. The defect predicate is therefore **"`task_identifier` present but not a valid UUID string"**, not "non-string `task_identifier`".

### The genuine self-healing counterexample (why this was subtle)

`task_identifier: "501"` (quoted, non-empty) takes a different path: the assertion succeeds, `taskID == "501"`, `isValidUUID("501")` is false, line 277 matches, and `injectAndStore(ctx, removeTaskIdentifier(content), ...)` strips the key before prepending. Converges in exactly one write. Quoting rescues `"501"` and does nothing for `""` — which is why the workaround below says "quote it with a non-empty value", not "quote it".

### Deterministic (unit-level, reproducible today)

Construct a `vaultScanner` with `autoInject=true` over a task file whose frontmatter is:

```
---
task_identifier: 501
status: in_progress
assignee: claude
---
body
```

Call `RunCycle` five times. Observed today: five writes, five appended UUID keys, `grep -c '^task_identifier:'` returns 6. Expected after the fix: one write, `grep -c '^task_identifier:'` returns 1.

## Expected vs Actual

| | Expected | Actual |
|---|---|---|
| `task_identifier` present but not a valid UUID string (any shape) | Treated as an invalid identifier: strip the bad key, mint one fresh UUID, converge in one write | Treated as a missing identifier: fresh UUID prepended, bad key retained, repeats every cycle forever |
| `task_identifier: ""` | Same as any other invalid identifier — stripped and replaced in one write | Indistinguishable from key-absent; raw content written; loops forever |
| Task file size under repair | Bounded — one `task_identifier` key | Unbounded — 3007 keys / 163 KB after 50h |
| Operator diagnostic | One warn log naming the file and the observed value's type | The `501` case emits no repair log at all, because the key-absent branch has none |

**Superseded once the guard lands, for one shape only.** This table states the contract of THIS spec alone. The one shape it does not converge is the uniformly indented frontmatter block (see Failure Modes): for that shape the "Expected" column reads *one write*, and `scanner-repair-convergence-guard` supersedes it to *zero writes plus a halt* and supersedes the "Task file size under repair" row's one-key outcome to "file untouched". The block-style shapes (AC2 rows 10-12) converge in exactly one write under this spec and are **not** superseded.

## Why this is a bug

The parse site loses information. Go's comma-ok type assertion is discarded with `_`, collapsing three distinguishable states (key absent / key present as a valid string / key present as anything else) into two. The branch at line 266 is documented and structured as the *key-absent* case — it deliberately passes raw content because there is nothing to strip. Feeding it a key-present case makes it write a file it has not repaired, and dedup's last-wins semantics guarantee that the next cycle observes the same trigger.

## Workaround

Operator-side, until the fix ships:

1. Replace the value with a non-empty quoted string: `task_identifier: "501"` -> the scanner self-heals in one write on the next cycle. An empty quoted string does NOT work.
2. Or delete the `task_identifier` line entirely -> the scanner mints a fresh UUID in one write.
3. If a file is already looping, scale the controller StatefulSet to 0 first, repair the file, then scale back up — otherwise the repair races the loop. The full procedure is operational knowledge and belongs in a runbook under `65 Runbooks/` in the Personal vault, not in this spec (see Non-goals); this line is the pointer, not the runbook.

## Goal

The vault scanner distinguishes `task_identifier` **absent** from `task_identifier` **present but not a valid UUID string**, and repairs the second case by stripping the offending key before minting a fresh UUID. Stripping is driven by the **parsed frontmatter key**, so every key spelling that YAML resolves to `task_identifier` — bare, double-quoted (`"task_identifier": 501`), single-quoted (`'task_identifier': 501`), or spaced before the colon (`task_identifier : 501`) — is actually removed instead of being silently missed by a raw line-prefix match. A uniformly indented frontmatter block is the one key spelling this Goal does not claim to converge: injection always prepends at column 0, so a surviving indented sibling key makes the file unparseable regardless of removal strategy, and that shape is the one bounded-but-corrupt case recorded in Failure Modes.

Every malformed shape in the AC2 table — including rows 10-12, the block-style sequence, the block-style mapping, and the block scalar — reaches **exactly one repair write in total**, is never written again, and leaves behind frontmatter that parses as valid YAML. Rows 10-12 converge only because removal is **span-aware**: it deletes the key line together with every following frontmatter line more indented than it, so no orphaned continuation line survives to fold into the freshly injected UUID (see the key-removal constraint in Constraints). No shape reaches one write per scan cycle forever, and the only shape this Goal does not claim to converge is the uniformly indented frontmatter block named above. The key-absent path and the healthy path are byte-for-byte unchanged, and content outside the frontmatter region is never modified.

## Non-goals

- Do NOT implement the convergence guard here — it ships in `scanner-repair-convergence-guard`. This spec closes the one known trigger; that spec bounds the class.
- Do NOT add a per-file write-rate circuit breaker (e.g. "max N writes per file per hour") — a rate limit slows an infinite loop rather than terminating it.
- Do NOT add commit-rate anomaly alerting on the vault repo — separate concern, separate spec, different owner (monitoring config lives in `bborbe/quant`).
- Do NOT redesign or reinstate the removed `AgentControllerWritebackFailing` alert — out of scope; tracked separately.
- Do NOT attempt to identify what originally wrote `task_identifier: 501` — open question, tracked separately. One plausible lead is `IncrementFrontmatterCommand` (`pkg/command/task_increment_frontmatter_executor.go`), which performs an atomic `+N` on a NUMERIC frontmatter key and would write an unquoted integer if it were ever misrouted to `task_identifier`. **This is UNVERIFIED** — no evidence in this incident links it to the write, and this spec must not be implemented as if it were the cause. The fix must hold regardless of origin.
- Do NOT change `DeduplicateFrontmatter`'s last-wins semantics — other callers depend on it and it is not the defect; the defect is writing a file whose duplicate keys were never removed.
- Do NOT change `AUTO_INJECT_TASK_IDENTIFIER` semantics from spec 001 — when the flag is `false`, every malformed shape still skips without writing.
- Do NOT publish a task whose `task_identifier` could not be repaired — a file with no valid identifier is not publishable, same as today.
- Do NOT document the operational recovery in this spec. "Scale the controller StatefulSet to 0, repair the file, scale back to 1" is durable operational knowledge with a lifetime longer than this fix, and belongs in a runbook under `65 Runbooks/` in the Personal vault — created separately, before or after this ships. The Workaround section below keeps a one-line pointer and nothing more; recovery steps must not accrete here.
- Do NOT add a config flag, environment variable, or opt-out that restores the old key-absent routing for non-string values — invariant; an escape hatch on the fix is the regression itself. If a future consumer demands variation, that is a separate spec.

## Desired Behavior

1. The frontmatter parse site distinguishes `task_identifier` **absent** from `task_identifier` **present**, using the map's presence check, and separately determines whether the present value is a valid UUID string, using the comma-ok type assertion result. Neither signal is discarded.
2. When `task_identifier` is absent, behavior is exactly as today: raw, unmodified content is passed to the injection path so that all other frontmatter keys, their order, and the body survive byte-identically.
3. When `task_identifier` is present but is not a valid UUID string — for any reason, including a non-string scalar, an empty string, a whitespace-only string, a sequence, a mapping, a block scalar, or a non-UUID string — the offending key is stripped from the content before a fresh UUID is prepended, so the written frontmatter contains exactly one `task_identifier` key.
4. Stripping the key modifies only the frontmatter region. Any line beginning `task_identifier:` that lives in the document body survives byte-identically.
5. A WARNING log covers the entire present-but-not-a-valid-UUID-string class, naming the file path and the observed value's Go type so an operator can tell from `kubectl logs` alone which malformation was repaired. The frozen greppable substring is `replacing invalid task_identifier`.
6. Files holding a valid, unique, string UUID `task_identifier` are never read differently, never written, and publish exactly as they do today — the fix is invisible on the healthy path.

## Design Decisions

- **Predicate is "present but not a valid UUID string", not "non-string".** The empty-string case proves the narrower predicate is wrong: `""` is a Go string, passes the type assertion, and still lands on the key-absent branch. A fix keyed on the type assertion alone would leave `""`, `''`, and `"   "` looping. Keying on presence-plus-UUID-validity covers both doors with one branch.
- **One frozen log substring for the whole class.** `replacing invalid task_identifier` supersedes the existing `replacing non-UUID task_identifier` line, giving the operator a single grep for every repair. The Go type is logged instead of the raw value so a large sequence or mapping cannot blow up a log line.
- **Removal must be frontmatter-scoped, key-based, AND span-aware. No part is optional, and the ACs pin all three.** The earlier framing of this bullet — that the implementer may keep the line-prefix scan because "AC5 passes either way" — was wrong and is retracted. AC5's fixture places `task_identifier: 501` at column 0 inside a fenced body block, so an unscoped remover deletes that body line and AC5 **fails**; the region boundary is pinned, not open. AC2 rows 14-16 place the key in spellings a line prefix never matches, so a scoped-but-still-prefix-based remover strips nothing, loops, and those rows **fail**. AC2 rows 10 and 12 place the value on continuation lines a line-only remover orphans; those orphans do not break the parse, they fold into the injected UUID as a multi-line plain scalar, so a key-aware but line-only remover loops (5 writes over 5 cycles, measured) and those rows **fail**. The three requirements compose without conflict: decide from the parsed frontmatter key which physical line(s) the key owns (or use an equivalent key-aware match that tolerates quoting, leading whitespace, and space before the colon), extend that decision over the key's full indentation span, and apply it **only within the frontmatter region**. Region scoping alone is insufficient; key-awareness alone is insufficient; line-only removal is insufficient.

## Constraints

- **Landing mechanism.** `.dark-factory.yaml` here is `workflow: direct`, `pr: false`, `autoMerge: false`, `autoRelease: false`, `defaultBranch: master` — dark-factory itself does not open or merge anything. The work happens on the feature branch `feature/task-identifier-convergence` and reaches `master` through a **manually opened** `gh pr create` per the Development Guide, reviewed and merged by the operator. The release tag is then cut by hand. This is why AC9's `git diff origin/master -- CHANGELOG.md` is the right comparison: the feature branch is ahead of an unmerged `master`.
- `DeduplicateFrontmatter`'s last-wins semantics are frozen — other callers depend on it, and it is not the defect.
- Spec 001's `AUTO_INJECT_TASK_IDENTIFIER` gate is frozen: when `false`, every malformed shape still skips without writing, and the frozen substring `AUTO_INJECT_TASK_IDENTIFIER=false; skipping task without valid task_identifier:` is unchanged (AC7 greps for it).
- The existing `(nil, "", false)` skip return shape and `(nil, relPath, false)` write return shape from `processFile` are frozen — downstream `scanFiles` bookkeeping depends on them and must not need changes.
- The zero-hash sentinel stored by `injectAndStore` (`hash: [32]byte{}`) is frozen — it is what makes the next cycle re-read and publish the repaired file rather than short-circuit at `pkg/scanner/vault_scanner.go:239`.
- **Hard constraint — key removal is key-based, is span-aware, and is confined to the frontmatter region. All three conditions hold; none is a suggestion and none may be traded for another.** `removeTaskIdentifier` (`pkg/scanner/task_identifier.go:33-45`) today matches the raw line prefix `task_identifier:` after a right-trim only, across the entire file, and deletes that one line. That is wrong three times over. (1) **Key-based, not prefix-based.** Removal must be driven by the **parsed frontmatter key** — either by deciding from the parsed frontmatter mapping which physical line(s) carry the key, or by matching the key line against `^\s*['"]?task_identifier['"]?\s*:`. A raw `strings.HasPrefix` match is not acceptable: it is a **verified** no-op for `"task_identifier": 501`, for `'task_identifier': 501`, for `task_identifier : 501`, and for an indented key inside a uniformly indented frontmatter block, while `DeduplicateFrontmatter` and `yaml.Unmarshal` resolve every one of them to the same `task_identifier` key. For the first three, prefix-based removal rewrites the file with a fresh UUID every cycle forever; AC2 rows 14-16 are the executable form of this half. The fourth is unfixable by removal alone and is handled as bounded-but-corrupt in Failure Modes. (2) **Span-aware, not line-only.** Removal must delete the key line **and every following frontmatter line more indented than it** — the full span of lines the parsed key owns, which is exactly what a block sequence, a block mapping, and a block scalar occupy. Deleting the key line alone is not acceptable, and the reason is not that it corrupts the document: **verified by executed simulation, it does not.** After the key line is removed and `InjectTaskIdentifier` prepends `task_identifier: <uuid>` at column 0, the orphaned continuation lines fold into that freshly injected UUID as a **multi-line plain scalar** — AC2 row 10 resolves to `task_identifier: "<uuid> - a - b"` and row 12 to `task_identifier: "<uuid> abc"`. Both are non-UUID strings, so the file re-enters the strip-and-reinject branch on every cycle: **measured 5 writes over 5 cycles under line-only removal, versus exactly 1 write under span-aware removal**, with the one-commit-per-minute loop left wide open for those two shapes. AC2 row 11 (block mapping) is the misleading case that made line-only removal look sufficient — its orphan genuinely fails `yaml.Unmarshal` and bounds that row at one write. Do not "simplify" this back to line-only removal on the strength of row 11: rows 10 and 12 reopen the loop. AC2 rows 10-12 are the executable form of this half. (3) **Frontmatter-region only.** The removal must never touch a line outside the frontmatter region, including a body line beginning `task_identifier:` at column 0 inside a fenced code block, and the indentation span in (2) terminates at the closing frontmatter delimiter. AC5 is the executable form of this half. An implementation satisfying only (1) and (3) leaves rows 10 and 12 looping; only (1) and (2) corrupts runbook bodies; only (2) and (3) leaves the commit storm uncured for the quoted and spaced key spellings.
- The log substring `replacing non-UUID task_identifier` is NOT frozen and may be superseded. Verified: no test, alert, or runbook greps it; the only other occurrence in the repo is a quotation inside `prompts/completed/002-spec-001-scanner-gate-and-tests.md`.
- Existing tests in `pkg/scanner/vault_scanner_test.go` and `pkg/scanner/vault_scanner_internal_test.go` must keep passing. That claim was verified for **behavioural** assertions only — no existing test asserts the buggy raw-content path for a present-but-invalid value. The check did NOT cover **source-structure** tests, and it missed the one described in the next bullet, which is the existing test this fix is most likely to break.
- **Hard constraint — the source-structure parity test.** `pkg/scanner/vault_scanner_test.go:1063-1095` (the `It` block; the two hardcoded `Equal(9)` assertions are at lines 1090 and 1093) shells out to `awk` over the range `/^func \(v \*vaultScanner\) (processFile|injectAndStore)\(/,/^}/` and asserts `skipCount == 9` **and** `counterCount == 9`, both hardcoded. The `//nolint` directive at `pkg/scanner/vault_scanner.go:227` records why: the three `AUTO_INJECT_TASK_IDENTIFIER=false` gates are inlined deliberately "to keep the parity-check awk range honest". The most natural implementation of DB1 — folding the now-identical key-absent and key-present-invalid auto-inject gates into one gate — drops a skip site to 8 and fails that test, and therefore fails `make precommit` (AC8). Rule: any commit that adds or removes a skip site must update **both** hardcoded counts and the `//nolint` rationale **in the same commit**. Reducing the site count while leaving the test at `9` is not acceptable, and neither is deleting or loosening the parity assertion to make a fold compile.
- The `writeCounterReset` path (empty -> named assignee transition) is untouched; it does not mint identifiers and is not a repair path.
- `CHANGELOG.md` exists in this repo (spec 001's claim that it does not is stale) — the entry goes under `## Unreleased`.
- AC2 rows 10-12 assert write count `1` **and** valid post-write frontmatter, and `scanner-repair-convergence-guard` does **not** supersede them — span-aware removal converges all three, so that spec's guard never fires on a block-style value. The one shape this spec leaves bounded-but-corrupt is the uniformly indented frontmatter block; that is the shape the guard supersedes, and the Expected vs Actual table and its Failure Modes row are marked accordingly. `scanner-repair-convergence-guard` AC2's block-style fixture is therefore no longer a non-converging input once this spec ships; that spec's Constraints record the substitution it must make.

## Security / Abuse Cases

The scanner parses operator- and agent-authored Markdown from a shared git repository, so frontmatter is untrusted input.

- **What an attacker (or a buggy writer) controls:** the entire YAML frontmatter of any task file, including the type, shape, and size of `task_identifier`, and the entire document body. This incident is the unintentional-abuse case: a single malformed scalar caused unbounded write amplification against a shared resource — a self-inflicted denial of service on the vault. The fix makes writes-per-file-per-content-state at most one.
- **What crosses a trust boundary:** the scanner's writes are committed and pushed to a repository other systems read. Every additional file this fix routes through `removeTaskIdentifier` is a file whose body could contain an attacker-chosen line beginning `task_identifier:`; AC5 is the boundary check that silent body deletion does not become a new abuse vector.
- **What can hang or retry forever:** the repair loop for the enumerated shapes — closed by this spec. The residual unenumerated case is explicitly the subject of `scanner-repair-convergence-guard`.
- **What must be validated:** `task_identifier` must be validated for presence, type, and UUID form before use, never coerced silently through a discarded type assertion. Deeply nested or very large values (a sequence or mapping under `task_identifier`) must not be interpolated into a log line — log the Go type and the file path, never the raw value's full contents.

## Do-Nothing Option

Not acceptable. The loop does not self-terminate — the production instance ran for 50 hours and stopped only because a human scaled the StatefulSet to 0. The cost of one occurrence was a 163 KB task file with 3007 keys, ~317 MB of parser warnings, and a vault-wide outage of `vault-cli task list`. The trigger surface is wider than it first appeared: not just an unquoted scalar, but also the empty quoted string, which is a shape this vault already writes routinely (`assignee: ""` in the incident probe fixture itself). No existing alert would catch a recurrence — the `AgentControllerWritebackFailing` alert that might have hinted at it was removed. Quoting values by hand is a workaround for one known bad file and, for the empty-string shape, not even that.
