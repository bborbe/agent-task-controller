## Summary

- Resolving one `task_identifier` to its task file costs a full vault walk: the lookup lists every task file and reads every one of them — 8,712 reads issued against an 8,972-file vault, ~11s per result write.
- That lookup runs on the single-threaded command consumer, so every result write blocks every other command behind it. The openclaw consumer drains a ~200-message backlog at ~0.6 msg/min.
- The measured consequence: an OpenClaw create-task command published at 14:35:44 was consumed at 15:11:27 — 36 minutes late — against a 60-minute expiry window, so commands are dropped as expired rather than processed.
- The fix publishes the identifier→path mapping the scanner already computes on every scan cycle, and consults it before walking the vault, turning a hit into one file read instead of 8,712.
- The full walk stays as the fallback for identifiers the index does not hold, and the fail-loud duplicate behaviour that prevents a result landing on the wrong task file is preserved.

## Problem

The controller's two halves run in one process on different goroutines: a polling scanner that detects vault changes, and a Kafka command consumer that writes results back. The consumer resolves a task file by listing the whole task directory and reading every file in it to find the one whose frontmatter carries the identifier it was handed — and it does that once per command, synchronously, on the consumer's single thread. On the openclaw vault that is 8,712 git-rest reads to resolve one identifier. The work the consumer does is therefore dominated by a lookup that has almost nothing to do with the command it is serving: ~11s of scanning to write one task's result. Because the consumer processes one command at a time, that cost is paid by every command queued behind it, so a routine burst of agent completions backs up past `commandExpireDuration` and the tail of the burst is dropped as expired rather than applied. The scanner, meanwhile, already holds exactly the mapping the consumer is recomputing — it knows every file's identifier, having parsed it to decide whether the file changed — and never publishes it.

## Reproduction

Environment: prod openclaw controller (`agent-task-controller-openclaw`, `taskDir: tasks`), measured 2026-09; this repo's newest release at measurement time is `v0.11.2` (`CHANGELOG.md:8`). The `dark-factory --version` field is not applicable — the defect is in this service, not in the pipeline.

**Measured on prod (the observed symptom).**

1. An OpenClaw create-task command is published to `agent-task-v1-request` at 14:35:44.
2. The same command is consumed at 15:11:27 — **36 minutes late**.
3. In the same window the controller's result-write path was measured at ~11s per command, driving the consumer's drain rate to ~0.6 msg/min against a ~200-message backlog.
4. The lookup's cost, measured in the same window: `FindTaskFilePath` (`pkg/result/result_writer.go:315`) lists the vault and reads every file through git-rest — **8,972 files in the vault, 8,712 file reads issued per lookup** (the 260-file delta is files the walk skipped rather than read: unreadable, invalid frontmatter, or short-circuited), **22 lookups in a 230s window** — one per 10.5s, which is one per consumed command, **not** one per `pollInterval` (60s).
5. The dominant log line, verbatim in shape from the capture (`pkg/result/result_writer.go:347`, V(3), repeated once per file read):

   ```
   ... result_writer.go:347] FindTaskFilePath: file tasks/<task-name>.md has task_identifier=<uuid>
   ```

   Of 193,262 lines in the 230s capture, **191,677 (99.2%) were this one line** — the walk is not merely the largest cost, it is almost the entire log volume.
6. Commands delayed past `commandExpireDuration = 60 * time.Minute` (`pkg/factory/factory.go:25-33` is the doc comment; the const itself is `:34`) are dropped as expired, so the 36-minute delay plus a 200-message backlog converts directly into lost frontmatter writes.

**Locally runnable reproduction (the same mechanism, counted instead of timed).**

1. Build a fixture vault under a temp `taskDir` holding N task files, each with a distinct `task_identifier` in its frontmatter; place the target identifier in the last file.
2. Drive one `WriteResult` for the target identifier through the result writer with a call-counting fake git client (`mocks.GitClient`, which records `ListFilesCallCount()` and `ReadFileCallCount()`).
3. **Pre-fix observation:** the fake records **1** `ListFiles` call and **N** `ReadFile` calls — the read count scales with the vault, not with the command, which is the whole defect.
4. **Post-fix observation:** the same `WriteResult` records **0** `ListFiles` calls and **1** `ReadFile` call.
5. Pre-fix, the same reproduction with the target identifier **absent** from the vault records 1 `ListFiles` and N `ReadFile` calls on each of the 3 retry attempts.

## Why this is a bug

The cost is not a slow-path inconvenience — it is the mechanism by which commands are lost, and the loss is exactly the outcome the `commandExpireDuration` doc comment forbids. `pkg/factory/factory.go:25-33` sizes the window at 60 minutes to absorb the worst-case queue residency of a 100+ task enqueue, and names the conditions it must survive: "a burst of agent completions, a slow git-rest round-trip, or a controller restart must not push tail commands past the window and silently drop their frontmatter writes." A lookup that reads every file in the vault on every command makes each of those conditions fatal, and the measured 36-minute delay plus a ~200-message backlog crosses the window in normal operation.

Two invariants must survive the fix, and each has a recorded incident behind it:

- **A duplicate identifier must never resolve to a path.** `pkg/result/result_writer.go:349-355` records the 2026-08-31 incident: the previous behaviour silently kept the last match from an unsorted `ListFiles`, which marked `Sentry Alert Fan-Out - 2026-08-31` done/completed carrying another task's analysis, for a run no executor ever performed. The lookup fails loudly instead, and any index that collapses duplicates silently reintroduces that bug.
- **A non-owning controller must not resolve a path it would not have resolved before.** `docs/controller-design.md:52` records that the vault-routing guard runs **before** the task-file lookup, so a cross-vault command "performs no vault scan, increments no metric, writes nothing, and publishes no result event". The guard's position relative to the lookup is part of that contract.

## Workaround

None that is user-side. The controller's `pollInterval` and the vault's file count are the cost's two factors; neither is an operator knob for this defect, and shrinking the window or the vault is not available. Operators can see the symptom (command lag, `agent_controller_git_rest_calls_total{op="list"}` rate, `agent_controller_results_written_total{result="not_found"}`) but cannot mitigate it from outside the process.

## Goal

A command carrying an identifier the controller's scanner has already seen resolves to its task file by reading exactly that one file, with no directory listing and no walk of the vault. The identifier→path mapping is built by the scanner, which already holds it, and published once per scan cycle in a form the command-consumer goroutine can read concurrently without racing the scanner. Identifiers the index does not hold — a file the scanner skipped, a file created since the last cycle — still resolve through the existing full walk, so no command that resolves today stops resolving. The fail-loud duplicate behaviour is preserved exactly: two files sharing one identifier produce the same error naming both paths, and no write happens. The end state is observable: the openclaw consumer drains its backlog at the rate the commands arrive rather than at the rate of a vault walk, so commands no longer expire before they are processed.

## Non-goals

- **The vault's written content.** The frontmatter merge and its ownership rules, the heal-on-write stamp, the escalation path, the supersede paths and the routing predicates are untouched. This fix changes how a file is *found*, never what is written to it.
- **The scanner's change detection.** The `hashes` bookkeeping, the content-hash short-circuit, the auto-inject gate, the convergence guard and the deleted-tasks stream keep their current semantics. The index is derived from that bookkeeping, not a replacement for it.
- **A second resolution mechanism.** No TTL, no expiry, no incremental update, no write-through invalidation. The index is rebuilt wholesale once per scan cycle and read between cycles. A finer-grained protocol is a separate change with its own failure modes.
- **Removing the full walk.** It stays, as the fallback for every identifier the index does not hold.
- **A knob.** No env var, config field, CLI flag or allowlist that disables or bypasses the index — invariant; a switch that restores the per-command walk re-opens this bug at the moment the vault is largest.
- **`commandExpireDuration`.** The window is not widened, narrowed, or made configurable. The fix is to stop paying the cost, not to tolerate it for longer.
- **Backfill.** Commands already dropped as expired stay dropped. The fix applies from the first command consumed after it deploys.
- **A new metric.** No new Prometheus counter or gauge is introduced. The hit is observable through the existing V(2) log line and the existing `agent_controller_git_rest_calls_total{op="list"}` counter.
- **An E2E scenario.** See the scenario-coverage note under Acceptance Criteria.

## Desired Behavior

1. **The scanner publishes the mapping it already holds.** Once per completed scan cycle — after the deleted-file collection step has returned, so the mapping is published even when the subsequent commit/push step fails — the scanner derives an inverse mapping from identifier to the path (or paths) carrying it, built from the same bookkeeping it uses to decide whether a file changed, and publishes it for readers.
2. **Publication is a whole-map swap under a read-write lock.** The scanner builds the new mapping and publishes it by replacing the previous one under a write lock; a reader takes a read lock and reads the published snapshot. A reader therefore observes either the previous cycle's mapping or the new one, never a partially built map and never a map being mutated. The scanner's own bookkeeping stays single-goroutine and unguarded, exactly as today — only the published snapshot is shared. The in-repo precedent for this shape is `pkg/result/result_writer.go:72-81` (`escalationCoalescingMutex`), a mutex guarding an in-process map with a doc comment naming what it protects.
3. **The resolver seam's contract is exact.** A small consumer-side interface resolves an identifier to a vault-relative task file path and reports one of four outcomes: the path with `found=true`; `found=false` with a nil error when the identifier is unknown; an error naming both paths when more than one file carries the identifier; and `found=false` with a nil error for the empty identifier, which is never indexed. A resolver error is an error, not a miss — the two mean opposite things, which is the same distinction `pkg/result/result_writer.go:311-314` records today.
4. **The scanner implements the seam without importing the consumer's package.** The scanner's interface gains the resolve operation so the scanner can be handed to consumers structurally, and the scanner package gains no dependency on the package that declares the seam. The constraint is decoupling, not a present-day import cycle: neither package imports the other today, so the edge would be new in whichever direction it were drawn; keeping it structural means the scanner's package stays free of a dependency on a consumer, and the frozen direction is "consumer declares, provider satisfies".
5. **The lookup consults the index first, with the walk as the fallback.** The shared lookup helper takes the resolver and: consults it first when it is non-nil; on a hit, reads that one file and parses its frontmatter, so a hit costs one read and no listing; if that single read or parse fails, falls back to the walk; on a miss, and when no resolver is supplied, runs the existing walk unchanged. A resolver error is returned as-is and does **not** trigger a walk. The existing retry loop (3 attempts, 1s backoff) and its logging are unchanged.
6. **One scanner instance is threaded to every consumer of the lookup.** The process constructs the scanner once and passes that instance both to the sync loop and to the command-consumer construction, which hands it to the result writer and to each of the four executors that resolve a path directly (the planning-retry gate included). Every production call site receives the real resolver; a nil resolver remains legal only as the test-friendly "no index" value. The position of each call site relative to the vault-routing guard and to input validation is unchanged, so the guard still runs first.
7. **The observable outcome is the cost change.** A result write for an identifier the index holds performs zero directory listings and exactly one file read, instead of one listing and one read per file in the vault, and the hit is recorded in the pod log at the deployed verbosity so a running controller's behaviour is readable rather than inferred. The command consumer is no longer serialized behind a full-vault walk per command, which is the property that keeps commands inside the expiry window.
8. **The documentation and the changelog record the change.** `docs/controller-design.md` § 1 states that the scanner publishes the identifier→path index, and § 2 states that the lookup consults it before walking the directory. `CHANGELOG.md` gains an `## Unreleased` bullet naming the index.

## Constraints

- **Import direction is frozen:** `pkg/scanner` must not import `pkg/result`. The seam is satisfied structurally.
- **The seam's name and shape are frozen:** `result.TaskPathResolver`, declaring the single method `Resolve(ctx context.Context, id lib.TaskIdentifier) (string, bool, error)`. `scanner.VaultScanner` gains `Resolve` with the same signature so the scanner satisfies the seam structurally. AC 8's `TaskPathResolver` grep in `pkg/factory/factory.go` checks this frozen public contract — a declared interface name, not an implementer's local variable spelling.
- **The scanner's bookkeeping stays unguarded.** `vaultScanner.hashes` (`pkg/scanner/vault_scanner.go:58`) keeps its single-goroutine access, written in `processFile` / `injectAndStore` / the empty-to-named reset path and read in `isIdentifierUnique` (`pkg/scanner/task_identifier.go:23`) and `collectDeleted` (`pkg/scanner/vault_scanner.go:495-519`). Only the published snapshot is locked.
- **The full walk is not removed.** `gitClient.ListFiles(taskDir+"/*.md")` plus the per-file read and parse stays as the fallback path inside the lookup helper.
- **The duplicate error's message shape is frozen:** `duplicate task_identifier %s in %s and %s` (`pkg/result/result_writer.go:357-361`). The two paths are the two carrying the identifier.
- **The retry loop is frozen:** `notFoundAttempts = 3` (`pkg/result/result_writer.go:271`) with its backoff, its retry log line and its `unowned` / `not_found` metric split (`pkg/result/result_writer.go:422-447`) are unchanged.
- **The lookup helper's signature is the shared contract.** It gains the resolver as a parameter; all five call sites use the new signature. No caller keeps the old one.
- **The five call sites keep their positions.** In each frontmatter executor the vault-routing guard and the identifier validation stay before the lookup; the guard's ordering is what `docs/controller-design.md:52` contracts.
- **A resolver miss is not an error.** The resolver reports absence with a nil error so the caller falls back; only an ambiguous identifier is an error.
- **Error wrapping uses `errors.Wrapf` from `github.com/bborbe/errors`** — never `fmt.Errorf`.
- **A nil resolver is a test-only value.** It selects the walk-only behaviour and is never passed in production.
- **Forbidden shapes**, each of which would satisfy a naive reading of the goal while breaking an invariant: exposing the live bookkeeping map by pointer to a reader; a package-level index variable; `init()` or `sync.Once` lazy wiring; a second goroutine added to "sync" the index; a package-level lookup function on the scanner called from the consumer's methods.
- **No new config field, env var, CLI flag, or metric.**
- **Frozen:** `commandExpireDuration` (`pkg/factory/factory.go:25-33`), the routing predicates, the frontmatter merge and its ownership table, the escalation path, the heal-on-write stamp.
- **`make precommit` and `make test` run from the repo root** (single Go module). The race detector is opted into with `ENABLE_RACE=true` (`Makefile.precommit:29-34`).
- The existing specs in `pkg/result/`, `pkg/scanner/` and `pkg/command/` pass with unmodified `Expect(` lines, apart from the mechanical argument additions the new helper signature forces.

## Assumptions

- The scanner observes every file the lookup needs. It records an entry only for files it fully processed; a file skipped for invalid frontmatter, a disabled auto-inject gate, or a repair that did not converge carries no identifier, and a file created since the last cycle has not been seen. These are the cases the fallback covers, and they are why the walk cannot be deleted.
- A cycle runs often enough that a file's absence from the index is transient. `pollInterval` defaults to `60s` (`main.go:61`) and the HTTP trigger (`main.go:234-238`) can force a cycle, so a freshly created task file enters the index within one interval.
- The scanner and the command consumer run in the same process on different goroutines — the scanner inside the sync loop's goroutine (`pkg/sync/sync_loop.go:62`) and the consumer on its own (`main.go:206-211`) — so an in-process published snapshot is reachable by the consumer. This is what makes an in-process index sufficient rather than a shared external cache.
- A vault task file's `task_identifier` is unique in practice; duplicates are the exception the fail-loud error exists for, and the 2026-08-31 incident is the recorded case.
- The measured prod numbers are the openclaw vault's: 8,972 files, 8,712 reads issued per lookup, 22 per-command lookups in a 230s window (one per consumed command — the 60s `pollInterval` is the scanner's cadence, not this one), ~11s per command, ~0.6 msg/min, and a ~200-message backlog. The personal controller's vault is smaller, so its delay is proportionally smaller and its commands expire less often.
- The deployed log level is 2, so a V(2) line is visible in the pod log the Post-Deploy ACs read.

## Security / Abuse Cases

- **What can an attacker control?** The `task_identifier` in a Kafka command payload. It is an agent-supplied value, so it crosses a trust boundary into the lookup. Pre-fix it is compared against parsed frontmatter values; post-fix it is a map key. The property that must hold either way is that **no path is ever constructed from the identifier** — the resolved path comes from the file list the scanner itself observed. An implementation that joins the identifier into a path (or treats it as a glob) would introduce traversal or glob-injection; the resolver returns only paths the scanner recorded.
- **What crosses a trust boundary?** Nothing new. The index is in-process, never serialized, never sent over the wire, never persisted. The Kafka payload, the vault's content and the git-rest responses are the same inputs as today.
- **Can the index be poisoned?** Only by writing to the vault: the keys are identifiers parsed from vault files, so poisoning the index means poisoning the vault, which is the same trust boundary the walk already reads through. A crafted identifier in a command cannot insert an entry.
- **Can a hostile stream grow or exhaust the index?** No — see the last two Failure Modes rows. The map's keys are the vault's identifiers, bounded by file count; the command stream only reads it.
- **What can hang or retry forever?** Nothing new. The walk fallback keeps the bounded 3-attempt loop with its 1s backoff (`pkg/result/result_writer.go:271`, `:382-420`). The index adds no I/O, no network call and no timeout.
- **Can the fix widen what a non-owning controller resolves?** No, provided the routing guard keeps its position before the lookup. That ordering is AC 9, and it is the reason the guard-vs-lookup line ordering is asserted rather than assumed.
- **What must be validated?** (a) The empty identifier is never indexed, so an empty key cannot match a file whose identifier is empty. (b) A resolver error is never treated as a miss, so an ambiguous identifier cannot be resolved by re-deriving the ambiguity. (c) The resolved path is one the scanner listed, never one built from the command payload.

## Do-Nothing Option

The bug stays and it is not marginal: every command that carries an identifier pays a full-vault walk, so the command consumer's throughput is set by the vault's size rather than by the commands. The measured cost is a 36-minute command delay and a ~0.6 msg/min drain rate against a 60-minute window, which means commands are dropped as expired rather than applied — silently, since an expired command's frontmatter write simply never happens. It also means the two failure conditions the `commandExpireDuration` comment explicitly names as survivable (a burst of completions, a slow git-rest round-trip) are not survivable today. The scanner already computes the mapping the consumer recomputes, so the fix is to publish what is already known rather than to build anything new; there is no cheaper moment to do it than now, and every cycle that passes costs the vault another walk per command.
