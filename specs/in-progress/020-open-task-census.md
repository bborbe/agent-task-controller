## Summary

- One new Prometheus series, `agent_controller_open_tasks{vault,phase,task_type}`, reports how many open records the controller sees in each `(phase, task_type)` pair of its own vault.
- It is a **level**: recomputed from scratch on the existing dedicated 60-second metrics ticker that spec 019 added, so it runs on the trigger-only deployments (`POLL_INTERVAL=0s`) where the scan cycle is dead.
- "Open" is `status` neither `completed` nor `aborted` — the same population the sibling task's SC1 pins. It deliberately includes `human_review` and `done`; the resting-phase exclusion belongs to the alert expression, not the instrument.
- A pair that empties is **deleted from the exposition**, not left at `0`, and the deletion is scoped to this controller's own `vault` value. This is the half a stale-label gauge gets wrong.
- Go change plus the metric contract written into `docs/controller-design.md` and one `## Unreleased` `CHANGELOG.md` bullet. The alert rule, the `bborbe/nuke` image bump and selector edit, and the dev/prod apply stay the vault task's own steps.

## Problem

The unreachable-phase check is a two-metric join. `bborbe/nuke`'s `agent/alerts/unreachable-phase-alert.yaml` (merged in PR #930, `aa31b1b8`, 2026-10-31) carries `agent_controller_open_tasks{phase!~"human_review|done"} unless on (phase, task_type) executor_config_accepted`, and the rule is already live on nuke dev — the `Alert` CR `unreachable-phase` exists in namespace `monitoring`, created `2026-11-01T09:45:35Z`, `for: 1h`, and evaluates `inactive` with `health: ok`. It reads healthy only because **both** sides of the join expose zero series: an empty right-hand side makes `unless` return the whole left-hand side, and an empty left-hand side makes it return nothing. The rule is loaded and silent; only its population is missing.

The vault side has no producer. The scanner already walks every agent record and already counts a subset — `countStuckPlanningTasks` tallies `github-update-go` records stuck at planning and exports `agent_controller_update_go_stuck_planning_tasks` — but the same walk never groups the population by `(phase, task_type)`. Without this gauge the join has nothing to subtract, so an agent record can sit in a pair no Config accepts with nothing counting it.

The obvious placement is a trap, and this repo has already paid for it once. `countStuckPlanningTasks` is called from `scanFiles`, which only runs inside `RunCycle`; all three nuke-prod controllers pin `pollInterval: "0s"` (`bborbe/nuke` `agent/values-prod.yaml` lines 344, 370, 397), so `RunCycle` never runs periodically. `CHANGELOG.md` **v0.22.6** records the consequence in this repo's own words: the capped-and-idle sweep added in v0.22.5 hung off `scanFiles` and was **dead code on prod**, measured 2026-10-28 with all three controllers `1/1 Running` and zero `escalateCappedIdle` lines. A census hung off the scan path would be dead in exactly the deployment the alert runs against.

⚠️ **Ordering hazard, recorded here because it constrains the deploy, not the code.** The alert is live now and safe because both sides are empty. The moment this gauge exists and `executor_config_accepted` does not, the `unless` has an empty right-hand side and returns the whole left-hand side — the rule then fires on **every open record** instead of on the defect. The executor-side metric must land first, or the alert must be held, until both halves exist. This spec cannot enforce that from inside this repo; it states it so the deploy order is explicit rather than discovered, and it is carried as a Failure Modes row as well.

## Goal

After this work:

- A running controller publishes one `agent_controller_open_tasks{vault="<its VAULT_NAME>",phase="<phase>",task_type="<task_type>"}` series per `(phase, task_type)` pair present among its open records, carrying the count as its value.
- The series is recomputed on the existing 60-second metrics ticker — once at start-up and once per tick — so it publishes under `POLL_INTERVAL=0s`, and it is never written by the scan cycle.
- A pair that empties disappears from the exposition entirely, and the deletion is scoped to this controller's own `vault` value, so a second controller's series are never touched.
- The metric contract — name, labels, the open definition, the empty-label rule, the clearing rule and the cadence — is written in `docs/controller-design.md`, and the change carries a `## Unreleased` `CHANGELOG.md` entry.
- `make test` and `make precommit` are green.

## Desired Behavior

1. **One labelled level series with a frozen surface.** `agent_controller_open_tasks` is a gauge vector registered in the `pkg/metrics` package, with exactly three labels in this declaration order: `vault`, `phase`, `task_type`. The declaration order is the argument order for both `WithLabelValues` and `DeleteLabelValues`, so it is part of the contract even though the DTO reports label names sorted. It is exposed through the `Metrics` interface with one accessor implemented by the default implementation and by the regenerated fake; the accessor's exact name and parameter order are the implementer's choice at impl time, while the metric name, the label names, the label order and the returned gauge type are frozen. The doc comment states that the value is a level rather than a counter and that a pair which empties disappears from the exposition instead of lingering at `0`. There is no `init()` pre-initialisation: the pair set is data-dependent, so a fresh pod has no census series until its first successful pass.

2. **What is counted.** A record is open when its `status` is neither `completed` nor `aborted`; an empty or unknown status is open, because it is not terminal. Its pair is `phase` and `task_type` read from the parsed frontmatter through the same extract → deduplicate → unmarshal → string-field path the existing scanners use, so a file whose duplicate keys deduplicate cleanly is counted once with the last value winning for each key. A missing or non-string `phase` or `task_type` contributes the **empty string** as that label value and the record is still counted — there is no normalisation, no sentinel and no filtering, because the alert expression owns every exclusion. A file that cannot be read, carries no frontmatter, or carries frontmatter that will not deduplicate or unmarshal is skipped silently and counted in no pair, so one broken file cannot blank the instrument.

3. **The value is a level count, published after the whole listing.** Counts are accumulated per pair across the entire listing and published only after the loop, so a pass abandoned mid-way publishes nothing at all rather than a partial board. Each pair's series is `Set` to its count. Nothing is incremented, accumulated or carried between passes, so two consecutive passes over an unchanged board publish identical values and the numbers are the board's counts rather than a running total.

4. **Vanished pairs are actively deleted, scoped to this controller's vault.** The scanner remembers the set of pairs it published in the previous pass. Every pair present in the current pass is published; every pair that was published before and is absent now has its series removed with `DeleteLabelValues(vaultName, phase, taskType)` — exactly the three label values in declaration order. The deletion is scoped to this controller's own `vault` value and must never be `Reset()`: three controllers run from one image, and `Reset()` would clear every vault's series, silently deleting another controller's census. A pair that empties therefore disappears from the exposition entirely rather than sitting at `0`; a pair that reappears later is re-created by the next `WithLabelValues`. An empty board leaves no census series for this vault and removes everything the previous pass published. There is no precedent to copy in this repo — `git grep '\.Reset()'` and `git grep 'DeleteLabelValues'` both return nothing on `origin/master` — so the implementer introduces the mechanism. Because the gauge is a package-level `promauto` variable and every spec reads the same `prometheus.DefaultGatherer`, each absence-asserting spec uses label values unique to itself — a distinct `vault` name or a sentinel pair — so a sibling spec's series cannot make the assertion order-sensitive.

5. **A sibling recompute on the existing metrics ticker.** The census is a separate recompute invoked from the same arm of `Run` that already drives the task-age pass: once before the loop when the metrics interval is positive — so a fresh pod publishes without waiting an interval — and once per tick. It never runs from `scanFiles`, from `RunCycle`, or from the start-up index build, and it is independent of `pollInterval`, so it publishes on a trigger-only controller. It is read-only: it lists the task directory, reads and parses each file, and publishes — it does not pull, scan, write, commit or send on the results channel. It is a **sibling** of the age pass rather than folded into it, because the two have different definitions and different failure modes and an early return or defect in one must not blank the other; they share the ticker arm and nothing else. Cancellation of the context abandons the pass at the next file boundary.

6. **Failure behaviour favours a stale value over a false zero.** A failed directory listing publishes nothing: the values from the previous successful pass stay in place and are never `Set` to `0`, because `0` would claim a clean board. On a pod's first failed pass nothing has been published yet, so the series are absent. One unreadable, frontmatter-less or unparseable file is skipped silently and counted in no pair. Because publication happens after the full loop, a cancelled or crashed pass leaves the previous values untouched.

7. **No configuration surface.** The census adds no environment variable, flag, chart value or interval knob, and `main.go` is unchanged: the cadence is the existing package-level `metricsInterval` constant of 60 seconds, passed through the constructor parameters that already exist. A deployed controller picks the census up on its next image deploy with no values change.

8. **The contract is written down and the change is recorded.** `docs/controller-design.md` gains a `## Open Task Census` section stating the series, its three labels, the open definition, the empty-label rule, the vanished-pair clearing rule, the 60-second cadence, and the fact that the resting-phase exclusion and the join against `executor_config_accepted` live in the alert — that section is the cross-repo contract `bborbe/nuke` consumes. `CHANGELOG.md` gains a `## Unreleased` bullet naming the series, because that is this repo's established convention and the repo's own releaser turns that section into a version on master.

## Constraints

- **Frozen metric name:** `agent_controller_open_tasks`. It is read by an alert expression that lives in `bborbe/nuke`; a rename breaks the join silently.
- **Frozen label names and declaration order:** `vault`, `phase`, `task_type`. The order is the argument order of `WithLabelValues` and `DeleteLabelValues`; a reordering is a silent mislabelling, not a compile error.
- **Frozen label value source:** the `vault` label is the scanner's configured vault name, passed through verbatim. The vault-api display name (`private-agent`) is a different naming scheme and must not be applied.
- **Frozen type and semantics:** a `GaugeVec`, whose value is a level count. A counter, a histogram or a summary is wrong; the alert subtracts series, and a counter would accumulate across passes.
- **Frozen open definition:** `status` neither `completed` nor `aborted`. The same population the sibling task's SC1 pins, so two readers count the same set.
- **Frozen placement:** the existing metrics ticker only — start-up plus each tick — never `scanFiles`, `RunCycle` or the start-up index build. `CHANGELOG.md` v0.22.6 is the record of what happens when a sweep is hung off the scan path on a trigger-only controller.
- **Frozen clearing mechanism:** `DeleteLabelValues` scoped to this controller's `vault` value. `Reset()` is forbidden — it clears every vault's series, and three controllers share one image.
- **Sibling recompute:** the census is its own recompute called from the ticker arm, not folded into the task-age pass. The two must be independently failable.
- **No new configuration:** `main.go` is untouched and no env var, flag or chart value is added.
- **Single writer:** the census is written only by the metrics ticker. `scanFiles` must not also `Set` it — two writers would make the value depend on which path ran last, and the scan path is dead on the deployments the alert runs against.
- **Existing behaviour untouched:** the age series, the stuck-planning gauge, the scan cycle, the identifier index and the escalation paths are unchanged.
- **The contract lives in the design doc.** `docs/controller-design.md` § Open Task Census is the cross-repo contract `bborbe/nuke` consumes. A change to the name, a label, the open definition or the cadence is a cross-repo change and needs its own spec that updates that section in the same change.
- **Single Go module; `make precommit` runs from the repo root.** The changed packages carry no Makefile.
- **Landing mechanism.** This repo sets `workflow: direct`, `pr: false` and `autoMerge: false`, so dark-factory commits straight to the branch it is given and opens no PR of its own. The merge is the operator's: `gh pr create` by hand when a PR is wanted, and the merge performed by a human. The Verification section's "after PR merge" rung heading describes the operator ladder, not a step any prompt performs.
- **The recompute runs inline in `Run`'s goroutine,** not in a second goroutine: the census and the age pass then never overlap, and a trigger arriving during a recompute waits in the buffered channel rather than being lost.

## Assumptions

- The dedicated metrics ticker added by spec 019 is present on this branch and runs at a fixed 60 seconds: `metricsInterval = 60 * time.Second` (`main.go:53`), wired at `pkg/scanner/vault_scanner.go:224-248` with a start-up recompute and a per-tick arm. The census reuses it rather than adding one.
- A deployed controller sets `VAULT_NAME` (it is a required setting today), so the `vault` label always has a value; there is no empty-vault case to handle.
- One controller serves one vault with a distinct `vaultName` — three nuke-prod controllers run from one image, each with its own name — so the `vault` label identifies the producer. Two controllers configured with the same `vaultName` would publish indistinguishable series; nothing in the gauge can separate them.
- The frontmatter helpers (`extractFrontmatter`, `DeduplicateFrontmatter`, the string-field reader) are shared and unchanged, so the census parses records the same way the existing scanners do.
- Prometheus exposition accepts empty label values, so a record with no `phase` or no `task_type` is a legal series rather than a malformed one.
- `DeleteLabelValues` is available on `*prometheus.GaugeVec` from the already-present `client_golang` dependency; no `go.mod` change is needed.
- The population is small and measured rather than assumed: on the `openclaw` vault (`private-agent`, `taskDir: tasks`) the 2026-11-01 read found **40 open records across 13 distinct pairs**, of which 2 carry an empty `task_type` and 1 an empty `phase`. The census therefore publishes roughly 13 series, and the empty-label case is small enough to publish faithfully rather than normalise.

## Failure Modes

| Trigger | Expected behavior | Recovery | Detection | Concurrency |
|---|---|---|---|---|
| The directory listing fails (git-rest error, vault unavailable) | The pass is abandoned before any value is written; the previously published values stay, and nothing is `Set` to `0`. On a pod's first pass nothing has been published yet, so the series are absent | The next tick recomputes; the census is correct again within one interval | Frozen values across successive scrapes, or no series at all on a fresh pod | The ticker runs in `Run`'s goroutine, so no second pass overlaps it |
| One file cannot be read, carries no frontmatter, or will not unmarshal | That file is skipped: it lands in no pair and the pass completes for every other file | The next successful pass counts it again if the file becomes readable | The pair counts sum to fewer than the number of open records | N/A |
| A pair empties (its last open record turns terminal or leaves the pair) | The series is deleted from the exposition; the scrape no longer carries the line | None needed — the deletion is the correct state. A pair that regains a record is re-created on the next pass | The line absent from `/metrics` while a sibling pair is present | N/A |
| A pass is abandoned mid-way (context cancelled, process restart) | Counts are published only after the whole loop, so nothing partial is written; previous values stay | The next tick or the next pod's start-up pass | A scrape showing the previous pass's values after a restart | Values are written after the loop, so a partial map is never published |
| **This gauge deploys before `executor_config_accepted` exists** | The alert's `unless` has an empty right-hand side and returns the whole left-hand side, so `unreachable-phase` fires on **every open record** within `for: 1h` — roughly 12 series on the openclaw vault today | Hold the alert, or land the executor-side metric first. `kubectl get alert unreachable-phase` returns to `inactive` once both halves expose series | The alert reads `Active` with a description naming records that already sit in an accepted pair | N/A |
| The full read takes longer than the metrics interval | The ticker drops the missed ticks and the next pass starts when the previous one returns; the value updates less often than the interval but never freezes permanently | The interval effectively becomes the read duration | The value's apparent cadence versus the fixed 60 seconds | Ticks are dropped, not queued, so no pile-up |
| Frontmatter schema drift — a record carries no `phase` or no `task_type` | The empty string is published as that label value and the record is still counted; no record is dropped and no sentinel is invented | None needed — the alert expression owns any exclusion | A series with an empty `phase` or `task_type` label | N/A |
| A bulk write flips many records' phases at once | The next pass publishes the new pair set and deletes the pairs that emptied; the census is a point-in-time snapshot | Automatic on the next tick | Several series disappearing and others appearing in one scrape | N/A |
| Two controllers configured with the same `vaultName` | Both publish the same label set; the gauge cannot distinguish them, so the series from the two targets are indistinguishable | Configure distinct vault names — one controller per vault is the deployed shape | Duplicate series with identical labels across targets | N/A |
| Pod restart | The census is unpublished until the start-up recompute completes, then published from scratch; the in-memory previous-pair set starts empty, which is harmless because the registry is empty too | The start-up recompute | A scrape gap of one pass duration | N/A |
| A trigger fires during a pass | The trigger waits in the buffered channel and the scan cycle runs immediately afterwards; no trigger is lost | Automatic | The scan cycle's own log lines | Single goroutine: the census, the age pass and the scan never run concurrently |

## Security / Abuse Cases

- **What can an attacker control?** Task frontmatter — `status`, `phase` and `task_type` — because agents and operators write those files. Every value is read defensively: a missing or non-string field becomes the empty label value, and an unparseable file is skipped. No file content reaches a log line, and no path, filename or record identifier ever becomes a label, so a crafted record cannot create a per-record series.
- **What crosses a trust boundary?** Nothing new. The census is a read-only consumer of files the scanner already reads; it adds no HTTP endpoint, no Kafka message, no write path and no new credential.
- **What can hang or retry forever?** Nothing new: the pass is a bounded loop over one listing with a context check per file, and it performs no retries. A slow store lengthens one pass and drops ticks rather than queueing them.
- **What is the label cardinality?** Bounded by the number of distinct `(phase, task_type)` pairs among open records — roughly 13 today — times one value for `vault`. It grows with the pair vocabulary, not with the record count, so a bulk write that assigns many distinct phases can raise it to at most the number of open records. That is the design's accepted ceiling, and it is far below a per-record series.
- **What must be validated?** The `vault` label must come from configuration, never from a file. The pair values come from frontmatter and are published verbatim, including the empty string — no normalisation is applied by design, and the alert expression is the place any exclusion is expressed. A non-positive metrics interval must never reach `time.NewTicker`, which the existing guard already covers.

## Suggested Decomposition

**Size acknowledged:** 8 Desired Behaviors × 23 Acceptance Criteria (184) across 4 code layers — the metrics surface, the census computation with its clearing rule, the ticker wiring, and the docs — exceeds both the `DB × AC > 50` and the > 3-layer thresholds. It stays one spec because the decomposition below gives every prompt a single independently verifiable outcome and no prompt spans more than two layers; splitting it would duplicate the frozen label-order and clearing-mechanism contracts across two specs.

|---|---|---|---|---|
| 1 | The metrics surface: the `agent_controller_open_tasks` gauge vector with its frozen name, three labels in declaration order and its doc comment, the interface accessor, the default implementation, the regenerated fake, and a `pkg/metrics` spec that gathers the registry and asserts the family, its gauge type and its exact label names | 1 | 2, 3 | — |

The DB column numbers the Desired Behavior entries; AC1 (`make test`) and AC23 (`make precommit`) are whole-repo gates satisfied once all four prompts have landed. Rationale: prompt 1 creates the series the rest writes through, so it comes first and is independently testable at the registry. Prompt 2 is pure computation over parsed files and needs no ticker, so it can be built and falsified entirely by unit specs. Prompt 3 is the only prompt that touches `Run`, which is where the whole-repo build gate lands — sequencing it after the computation keeps the compile breakage confined to one prompt. Prompt 4 writes the contract and the release record from what prompts 1-2 built and touches no code. The alert rule, the `bborbe/nuke` change and the deploy are the vault task's own subtask 4, not this spec's.

## Do-Nothing Option

Safe but insufficient. Nothing is broken today: the alert is live and silent precisely because both sides of the join are empty, so doing nothing keeps the fleet in its current state. But that state is the defect — `agent_controller_open_tasks` has no producer, so the join can never fire, and a record sitting in a pair no Config accepts stays invisible to every instrument the fleet has. The cheap-looking alternative — hang the census off the existing scan — would ship a series that is dead on all three nuke-prod controllers, which is worse than no series at all: it would read as solved in review while the alert's left-hand side stayed empty on the only environment that matters, and this repo has already recorded that exact failure once in `CHANGELOG.md` v0.22.6. The change is one gauge vector, one read-only pass and one call added to an existing ticker, so there is no cheaper moment than before the executor half is built on top of it — and the ordering hazard means the cheaper moment is now, while the alert can still be held.
